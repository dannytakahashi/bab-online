## iOS reconnect after a background

- iOS reconnect after a background (owner 2026-11-12, "buttons aren't responsive ... after it supposedly is reconnected"): Socket.IO-Client-Swift 16.1.1, once reconnecting, schedules its next attempt after every connect (`_tryReconnect`: 1.5^n s with jitter, at most `reconnectWaitMax` 5 s) whether or not that handshake answered, and nothing can fire or cancel the tick. So (a) a foreground between two attempts (manager `.notConnected`, socket `.connecting`: a deploy or a network drop during the ~30 s keep-alive) waited up to 5 s for the tick with nothing in flight, and (b) on a slow link (a polling handshake over ~1.5 s) a tick starts a second handshake on the same engine beside the first, and the late answer to the first can be taken for the second, losing the namespace connect (no `.connect`, no restore; read from the library source, not reproduced with a 2.5 s server-side handshake delay) until the server drops the engine (connectTimeout: 45 s by default, now 10 s, `serverOptions.js` above). `SocketManager.reconnect()` and the old namespace leave + join go through the same ticks. `SocketService.forceReconnect` (a foreground after the keep-alive whose connection fails the keep check in the next bullet, or inside the keep-alive while not connected; sign-out) therefore never reconnects the old manager: it retires it (`retire`: handlers removed, `reconnects = false`, `disconnect()` so its pending tick returns, socket removed so a late handshake answer joins no namespace) and builds a new manager + socket (`makeConnection`, this service's handlers + `eventRouter.registerAll()`), whose one handshake starts at once with no tick scheduled. The library still overlaps handshakes in its OWN reconnects on a slow link (a deploy while the app is in front); the server's 10 s connectTimeout bounds that. `isConnected` and `isSessionReady` go false on any non-connected `statusChange` (a library reconnect sends no `.disconnect`). Session gate: `.connect` fires before the restore answers, and a New Game tapped in that window made a lobby that the restore's `joinMainRoom` then left (`mainRoomHandlers.joinMainRoom` from a socket in a lobby runs the Leave flow: `leftLobby` + `mainRoomJoined`, `lobbyPlayerLeft` to the others, kept as the safety net for 1.1.0 / 1.2.0; `joinMainRoomInLobby.test.js`), so `SocketService.isSessionReady` is false from every `.connect` until sign-in / sign-up / the restore succeeded and its follow-up emit went out (`noteSessionEstablished`; per-socket order puts a later tap behind it), and the main room's New Game (with its Tournament choice; until 2026-11-26 a Tournament button of its own), Join and Spectate are disabled until then (fixture `-uiSessionPending YES`). Tests: `ForegroundReconnectTests` (a real manager mid-backoff against a refused local port), `SessionPendingTests` (UI). Ships with the next iOS build
- Keeping a live connection (owner 2026-11-14, "one extra restore after a long background"; iOS 1.2.1 build 9): a foreground after the keep-alive (`AppPresence.handleScenePhase`, `isBackgroundTaskActive` false) calls `SocketService.resumeAfterKeepAlive`, which no longer replaces a connection that is alive, including one the library already reconnected and restored in the background (it was replaced anyway: ~2 s of Reconnecting and restore for nothing). Decision (`foregroundCheck`, from state alone): no manager / socket, socket status not `.connected`, manager status not `.connected`, `isConnected` false, or `isSessionReady` false (restore not answered, or nobody signed in) -> `forceReconnect` at once, exactly as before. Otherwise a status flag is not proof (the 2026-11-12 bug was a socket that said connected with its namespace lost), so it is probed: `requestSnapshot {requestId: "fg-N", log: false, customPics: false}` on that socket; `stateSnapshot` with that requestId within `foregroundProbeTimeout` (1.5 s) -> kept (no new manager, no handshake, `isConnected` / `isSessionReady` never change, so no toast); no answer by then, or any non-connected `statusChange` / `.disconnect` of that socket meanwhile -> `forceReconnect` then. While the probe is in flight (`isForegroundProbing`) the main room's New Game (a tournament included), Join and Spectate are disabled (`canSendMainRoomActions` = `isSessionReady && !isForegroundProbing`; an action sent then could go out on a socket the probe retires, and be lost), with no toast or other reconnect UI (a live link answers in milliseconds); released on the answer, and on a rebuild the flag drops only after `forceReconnect` has set `isSessionReady` false, so the session gate takes over with no gap (fixture `-uiForegroundProbe YES`, `SessionPendingTests`). No wire change: the server already answers requestSnapshot on the asking socket (`not_in_game` outside a game). The answer also goes through the router like any snapshot, so mid-game it is the table resync the restore's rejoin would give (`applySnapshot`); it arrives after every event the server sent that socket while the app was away (one ordered stream), so `log: false` keeps the log already in the store. The main room re-joins on its own foreground (`MainRoomView`); a lobby or tournament screen gets nothing more (on a kept socket nothing was missed). The probe is dropped by a new background (`beginBackgroundKeepAlive`), `forceReconnect` (sign-out) and `disconnect`; a late answer to a dropped or timed-out probe does nothing; its handlers are removed by id (`off(id:)`, never `off(event)`, which would remove the router's stateSnapshot handler). Within the keep-alive the foreground is unchanged (`forceReconnect` only if not connected). Logs: `[Socket] Foreground: probing connection <sid> (fg-N)`, `... connection kept (fg-N answered in N ms)`, `... rebuilding connection (<reason>)`, `[Socket] New connection #N` (`connectionsOpened`).
