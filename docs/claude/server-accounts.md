# Server: accounts, sessions and sign-in

Never auto-loaded: open it for sign-in, sessions, sign-up names, password hashing or the sign-in throttle (`server/socket/authHandlers.js`, `server/socket/sessionIdentity.js`, `server/utils/`).

## Sessions and socket identity

- Sessions are per device (`server/utils/sessionTokens.js`): each sign-in adds a token to `users.sessionTokens` (SHA-256 hashes only, max 5, expire 90 days after last use) instead of replacing the old one, so signing in on the computer doesn't log the phone out. A legacy plaintext `users.sessionToken` is still accepted (with no expiry) and migrated on its next use; `scripts/migrate-legacy-session-tokens.js` (owner-run, not run yet: whether any remain in production is unknown) folds the rest in at once (`server/admin/legacySessions.js`: the write verifySession would make, guarded on the token and sessionEpoch; tombstones only unset; counts only). Only one *live* socket per user: a password sign-in, or a different device restoring its token, kicks the previous socket (`forceLogout`); the same device reconnecting (same token hash in `socket.data.sessionHash`) does not. `rejoinGame` from an unauthenticated socket (web reload mid-game) is authorized by the same `verifySession` check on the token it sends. Rejoining a tournament game also reattaches tournament membership to the new socket. Identity is per SOCKET (`server/socket/sessionIdentity.js`): `GameManager.registerUser` keeps one entry per username AND per socket and returns the socket the name was on; signIn / restoreSession / signUp / a token rejoin as ANOTHER account first `releaseIdentity` (the disconnect bookkeeping without closing the socket: game seat to grace, lobby left at once, tournament, spectating, every room, claim, session hash, block list), and `signOutUser` / `disconnectPreviousSocket` never touch a socket that is another account now (`belongsTo`; users.socketId of the old account can still name it) (`socketIdentity.test.js`). Supersede (owner live check 2026-11-11: a second web tab left the first one dead): when the name's previous socket is still connected with the SAME session hash (a tab adopting the saved session, a reload whose old socket the server still holds), signIn / restoreSession park it once the sign-in stands (`markSuperseding` at registerUser, `cancelSupersede` if the re-check undoes it, `confirmSupersede`): s2c `sessionSuperseded {reason: 'newerConnection'}` (web only; Swift excluded), out of the main room and spectating, its lobby seat held (the lobby grace below), its claim kept (signOutUser still reaches it); a game seat moves with the newest socket's rejoin as before. A packet gate (`socket.use(supersededGate)`) drops every event a parked socket sends except signIn / signUp / restoreSession / clientHello and answers `sessionSuperseded {refused}` at most once a second, never `serverError` (a client would toast and resync; iOS has no sessionSuperseded handler and never shares a token between live sockets). A different hash still gets forceLogout. Restoring on the parked socket takes the session back, with its lobby seat in place if that is still held for it (`clearSuperseded` -> `GameManager.resumeHeldLobbySeat`; a re-sent joinLobby for the lobby a socket already sits in just answers lobbyCreated); a parked socket switching accounts gives that held seat up at once (`releaseHeldLobbySeat` in releaseIdentity, no leftLobby to the new account). A lazy / resigned seat rejoined from the newest socket does not demote a parked previous socket to spectator (`seatLifecycle.watchSeat`: it just leaves the room). Web: `ui/components/SupersededNotice.js` (a `pinned` kit modal: one opened while it is up, e.g. a resignation offer or the score modal still reaching the parked tab, goes in under it, inert, without focus, and becomes live when it closes; alertdialog, not dismissible, focus on Use here, opaque backdrop); while parked `ClientSession.park()` blocks `resume()` and `SocketManager.setParked` blocks the background ping and forced reconnects, voice stops; Use here = unpark + `forceReconnect` (a fresh socket restores and re-enters the screen); a restore / sign-in answer or forceLogout lifts it (`sessionSuperseded.test.js`, `client/src/reload/supersededTab.test.js`). The other tab closed (2026-11-11): when the user's LIVE socket disconnects (`queueHandlers.handleDisconnect`, not an account switch) and a parked socket of that user is still connected, `sessionIdentity.liveSocketClosed` tells the parked ones `sessionSuperseded {reason: 'otherClosed'}` after `OTHER_CLOSED_DELAY_MS` (2 s) unless a socket holds the session by then (a reload of the active tab: nothing sent); a sign-in / restore after that sends 'newerConnection' again to those (`reparkClosedNotices`); refusals carry the reason last told. Web changes the notice's text in place ("The other BAB Online tab was closed. Use here to continue.", focus stays on Use here, polite live description); nothing is taken back by itself (`parkedOtherClosed.test.js`, `client/src/reload/supersededTabClosed.test.js`)

## Username rules

- Username rules for NEW sign-ups (owner, 2026-11-11; `server/utils/usernameRules.js`, checked first in `signUp`, before the profanity filter and any DB read): 3-20 characters of ASCII letters, digits, space, `_ - .`; starts with a letter or digit; no space at either end (iOS 1.1.0 sends the field as typed, web trims), no double space; no emoji, which also keeps humans off every bot name (bots are always `🤖 <persona>` / `🤖 Bot N`). Each refusal is its own `signUpResponse {success:false, message}` (web: toast "Registration failed: <message>", iOS 1.1.0: red text under the fields); Joi stays at 1-50 so a long name gets the rule message, not a validation error. Taken = an existing user ignoring case and whitespace around the stored name (`findNameClash`: exact `findOne` first, so a merged tombstone keeps its redirect, then an anchored, escaped `$regex` with `i`; no index, no migration, stored names never rewritten): "That name is taken." / `That name is taken: "Alan T" already exists, and capital letters don't make a different name.` Sign-up budget, per socket: the wrapper's `rateLimiter.signUp` (20 / 5 min, `serverError {code:'rateLimit'}`) counts every attempt; refusals by these rules, the profanity filter and the taken check spend only that, and only an attempt past them (bcrypt hash + insert) also spends `signUpAccount` (3 / 5 min, checked in-handler; over it `signUpResponse` "Too many sign-up attempts..."), so trying names never locks a player out. That attempt also takes a token from budgets a reconnect does not reset (`rateLimiter.buckets`, `authHandlers.takeSignUpSlot`, 2026-11-15): `signUpIp` per client IP (`socket.data.clientIp`, an IPv6 address by its /64 through `clientIp.ipBucketKey`, the reset route's key; 5 at once, then 5 an hour), `signUpNet48` per IPv6 /48 (`clientIp.ipNet48Key`; 10 at once, then 10 an hour; one VPS or customer allocation holds 256 to 65,536 /64s; IPv4 has no such tier), both skipped when the IP is unknown (never one shared key), and `signUpGlobal` for the whole server (20 at once, then 60 an hour). All of them are checked before any is spent, and before `signUpAccount`, so a refused attempt writes no key and retrying after it never turns into the per-socket message. Over any: `signUpResponse {success:false}` with "Too many new accounts from this network. Please try again in N minutes." / "Too many new accounts are being created right now. Please try again in a few minutes.", and at most one warn line a minute per kind ('Sign-up ceiling reached: refusing new accounts server-wide' / 'Sign-up refused: per-IP account limit' with the bucket, with `refusedSinceLastLine`). A busy hash pool gives the tokens back. Refilled buckets are dropped by the rate limiter's 5-minute sweep; at 10,000 keys only refilled keys make room and a map full of spent keys refuses new ones (fails closed, as signInThrottle), so rotating addresses never resets a spent key. Known trade-off: about 12 IPv4 addresses or /48s kept busy can hold the server-wide ceiling empty, refusing every new account (never a sign-in) until they stop; its warn line is the one to alert on. Tests: `server/socket/__tests__/accountLimits.test.js`. Existing accounts keep their names (including ones these rules refuse) and sign-in, restoreSession, profile lookups and merges stay exact. Tests: `server/socket/__tests__/signUpNames.test.js`, realMongo (b)
- Reserved names (2026-11-15; `usernameRules.RESERVED_NAMES` / `isReservedName`, the last check in `checkNewUsername`, so sign-up AND the admin rename refuse them): system, admin, administrator, moderator, mod, babonline, bab, server, support, official, staff, bot, null, undefined, population (the leaderboard's average row). A name is reserved when, spelled as the filter reads a handle (any case, leetspeak undone, separators, digits and repeated letters dropped) with the lookalikes l / i and rn / m read alike, it is one of these or several run together ("SYSTEM", "Adm1n", "Bot 2", "Official_Support", "BabOnline Staff", "Admln", "Systern"), a staff plural (`RESERVED_PLURALS`: admins, administrators, moderators, mods, officials, bots), or one with `RESERVED_QUALIFIERS` around it (the, real, team, squad, crew, notice(s), alert(s), account, help, desk: "The System", "Admin Team", "System Notice", "Mod Squad"); a name that only contains one, or only qualifiers, passes ("Bobcat", "Model", "Babs", "Systems Guy", "Help Desk", "Theo"). Reply: `signUpResponse {success:false, message: "That name is reserved. Please choose another."}`. Bot persona names (Mary, Sharon, Danny, Mike, Zach) stay free: bots always show as `🤖 <persona>` / `🤖 Bot N`, and the emoji rule keeps humans off those. Existing accounts are never re-checked; no seeded or fixture name collides (test1, the Apple review account, is neither reserved nor filtered)
- Username profanity filter (2026-11-15; `server/utils/profanityFilter.js` `containsProfanitySubstring`, after the format rules; sign-up and admin rename; "That username is not allowed."): the handle is lowercased and each letter of a term may repeat ("fuuuck"). A term counts only inside one WORD of the handle (review fix, same day: matching across words refused "Matt Watson", "James Luther", "Hanna Ziegler", "Josh17"): words end at separators, at a digit that is not leetspeak, and at a camelCase break between two parts of 3+ letters ("MattWatson"; random capitals like "FuCking", "NiGger" are no break); runs of 1-3 letter fragments are read as one word ("f.u.c.k", "sh_it", "fu2ck"); the `COMPOUND_TERMS` (asshole, dickhead, cocksucker, motherfucker, wetback) also count across words ("AssHole", "Dick_Head"). Leetspeak (0 o, 1 i and l, 3 e, 4 a, 5 s, 7 t, 8 b) is read inside a word, but a trailing number of 2+ digits stays a number ("Josh17", "Ash17") unless it finishes a term that starts the word ("sh17"). `EMBEDDED_TERMS` count anywhere inside a word ("xXfuckXx", "BigNazi88", "rapist_joe", "TheRapist") unless wholly inside an `ALLOWLIST` word (Scunthorpe, therapist, -twater as in Atwater / saltwater, snigger, niggard, retardant, retardation, shiitake / mishit and a few Japanese surnames, Ashkenazi and the names Nazir / Nazim / Nazia, pussyfoot, pussycat) or the word is exactly one of `ALLOWED_NAMES` (Ishita, Nishita, Harshit, Akshita, Kshitij, Shital, Nazila, Slutsky, ...; exact, so "shitall" is refused); the short `WORD_TERMS` (fag, spic, kike, chink, dyke, rape, pedo, prick, kys) only as a whole word, split at every capital ("MrFag", "Big_Spic"; not Spice, Grape, Torpedo, Fagan). Names with no term pass however they look (Dickens, Hancock, Sussex, Cocktail, Assassin). Accepted false positives: a name run into the next in lower case ("mattwatson", "joshito"), two short parts that join into a term ("Ash It"), the surname Dyke as its own word ("Van Dyke"), a compound across words ("Sweet Back"); extend `ALLOWED_NAMES` (a given name) or `ALLOWLIST` (a word part, never a fragment like "shita") when one is reported. Chat (`filterProfanity`, every chat surface and lobby names) masks with `*`, same length, by the same word rules except that only single letters join ("f.u.c.k", "s h i t"): an embedded term masks its whole word ("fucking", "bullshit", "shitty", "MotherFucker"), never punctuation or digits at its ends ("shit!" → "****!"), and the word terms mask their listed forms ("rapes", "raping"); names in chat stay ("Ishita", "Josh17", "MattWatson"). Chat text is folded first (zero-width characters and combining marks dropped, fullwidth / accented letters and Cyrillic / Greek lookalikes read as Latin: "fu\u200Bck", "fu\u0441k"); still open: wildcards ("f*ck") and sound-alikes ("phuck"). Letter runs are cut to two before matching, so a long run cannot make the patterns backtrack. Tests: `server/utils/__tests__/profanityNames.test.js` (tables), `profanityFilter.test.js`, signUpNames.test.js, adminPanel.test.js (rename)

## Password hashing

- Password hashing (`server/utils/passwordHash.js`): bcryptjs (same `$2a$`/`$2b$` cost-10 format, no migration) in a `worker_threads` pool (`BAB_HASH_WORKERS`, default 2; lazy, unref'd while idle; >50 pending → `HASH_BUSY` → "Server is busy"; new hashes (sign-up, a reset link) may hold only 20 of the 50 (`MAX_PENDING_HASH`), so a sign-up flood leaves 30 places for compares and a real sign-in or delete-account check is still answered (a compare queued behind 20 hashes waits about 20 x 70 ms / pool size); `_setRunnerForTests` runs a fake slow hasher with the same queue limits (`accountLimits.test.js`); a crashed worker's jobs re-run inline). Inline bcryptjs when the Worker constructor throws and under Jest unless `BAB_HASH_POOL=1` (`server/utils/__tests__/passwordHash.test.js`). The CLIs (`setPassword`) keep plain bcryptjs

## Failed-sign-in throttle

- Client IP behind Railway (`server/utils/clientIp.js`): verified 2026-11-15 that Railway's edge overwrites a client-supplied X-Real-IP / X-Forwarded-For (failed sign-ins sent with forged headers were throttled and logged under the sender's real IP), so the per-IP sign-in and sign-up keys cannot be rotated by forging headers
- Failed-sign-in throttle (`server/socket/signInThrottle.js`): failures only (unknown user, wrong password; not merged-account redirects, DB errors or HASH_BUSY), 15 min sliding window: (ip, username) pair 10, ip 50, username 30 (pair and ip skipped when the IP is unknown); a success clears the pair; an (ip, username) that signed in or restored a session in the last 30 days is known-good and skips the username key (an outsider's guesses cannot lock out the household); a flood never evicts a key at its limit (a map full of lockouts fails closed for new keys); checked before any DB read and answered with the usual `signInResponse` failure. The pair/username keys are reserved synchronously with the check (no overshoot from parallel guesses); the ip key counts confirmed failures only (a family signing in together behind one NAT never blocks itself). deleteAccount's password check counts exactly like a sign-in (2026-11-15: check before the DB read, reserve, a wrong password confirmed, a right one clears the pair; throttled → `deleteAccountResponse {success:false, message: 'Too many incorrect passwords...'}`), so a hijacked signed-in socket cannot guess the password through it across reconnects. restoreSession/rejoinGame/signUp never count here (restoreSession and rejoinGame have only per-socket limits, 10 a minute, which a reconnect never meets: each reconnect is a new socket; signUp has its own budgets above). Client IP (`server/utils/clientIp.js`, `socket.data.clientIp` at connection): a public handshake peer is used as-is (headers ignored); behind a proxy/private peer (Railway's edge is in 100/8) `X-Real-IP` when it is a non-proxy IP that appears in `X-Forwarded-For` (or XFF is absent); the leftmost XFF entry alone is never trusted; else null and only the username key applies (never one shared key). Every password sign-in logs 'Sign-in client address' (peer, X-Real-IP, XFF, chosen ip): check it after a deploy that different networks get different IPs
