# Server: accounts, sessions and sign-in

Never auto-loaded: open it for sign-in, sessions, sign-up names, password hashing or the sign-in throttle (`server/socket/authHandlers.js`, `server/socket/sessionIdentity.js`, `server/utils/`).

## Sessions and socket identity

- Sessions are per device (`server/utils/sessionTokens.js`): each sign-in adds a token to `users.sessionTokens` (SHA-256 hashes only, max 5, expire 90 days after last use) instead of replacing the old one, so signing in on the computer doesn't log the phone out. A legacy plaintext `users.sessionToken` is still accepted and migrated. Only one *live* socket per user: a password sign-in, or a different device restoring its token, kicks the previous socket (`forceLogout`); the same device reconnecting (same token hash in `socket.data.sessionHash`) does not. `rejoinGame` from an unauthenticated socket (web reload mid-game) is authorized by the same `verifySession` check on the token it sends. Rejoining a tournament game also reattaches tournament membership to the new socket. Identity is per SOCKET (`server/socket/sessionIdentity.js`): `GameManager.registerUser` keeps one entry per username AND per socket and returns the socket the name was on; signIn / restoreSession / signUp / a token rejoin as ANOTHER account first `releaseIdentity` (the disconnect bookkeeping without closing the socket: game seat to grace, lobby left at once, tournament, spectating, every room, claim, session hash, block list), and `signOutUser` / `disconnectPreviousSocket` never touch a socket that is another account now (`belongsTo`; users.socketId of the old account can still name it) (`socketIdentity.test.js`). Supersede (owner live check 2026-11-11: a second web tab left the first one dead): when the name's previous socket is still connected with the SAME session hash (a tab adopting the saved session, a reload whose old socket the server still holds), signIn / restoreSession park it once the sign-in stands (`markSuperseding` at registerUser, `cancelSupersede` if the re-check undoes it, `confirmSupersede`): s2c `sessionSuperseded {reason: 'newerConnection'}` (web only; Swift excluded), out of the main room and spectating, its lobby seat held (the lobby grace below), its claim kept (signOutUser still reaches it); a game seat moves with the newest socket's rejoin as before. A packet gate (`socket.use(supersededGate)`) drops every event a parked socket sends except signIn / signUp / restoreSession / clientHello and answers `sessionSuperseded {refused}` at most once a second, never `serverError` (a client would toast and resync; iOS has no sessionSuperseded handler and never shares a token between live sockets). A different hash still gets forceLogout. Restoring on the parked socket takes the session back, with its lobby seat in place if that is still held for it (`clearSuperseded` -> `GameManager.resumeHeldLobbySeat`; a re-sent joinLobby for the lobby a socket already sits in just answers lobbyCreated); a parked socket switching accounts gives that held seat up at once (`releaseHeldLobbySeat` in releaseIdentity, no leftLobby to the new account). A lazy / resigned seat rejoined from the newest socket does not demote a parked previous socket to spectator (`seatLifecycle.watchSeat`: it just leaves the room). Web: `ui/components/SupersededNotice.js` (a `pinned` kit modal: one opened while it is up, e.g. a resignation offer or the score modal still reaching the parked tab, goes in under it, inert, without focus, and becomes live when it closes; alertdialog, not dismissible, focus on Use here, opaque backdrop); while parked `ClientSession.park()` blocks `resume()` and `SocketManager.setParked` blocks the background ping and forced reconnects, voice stops; Use here = unpark + `forceReconnect` (a fresh socket restores and re-enters the screen); a restore / sign-in answer or forceLogout lifts it (`sessionSuperseded.test.js`, `client/src/reload/supersededTab.test.js`). The other tab closed (2026-11-11): when the user's LIVE socket disconnects (`queueHandlers.handleDisconnect`, not an account switch) and a parked socket of that user is still connected, `sessionIdentity.liveSocketClosed` tells the parked ones `sessionSuperseded {reason: 'otherClosed'}` after `OTHER_CLOSED_DELAY_MS` (2 s) unless a socket holds the session by then (a reload of the active tab: nothing sent); a sign-in / restore after that sends 'newerConnection' again to those (`reparkClosedNotices`); refusals carry the reason last told. Web changes the notice's text in place ("The other BAB Online tab was closed. Use here to continue.", focus stays on Use here, polite live description); nothing is taken back by itself (`parkedOtherClosed.test.js`, `client/src/reload/supersededTabClosed.test.js`)

## Username rules

- Username rules for NEW sign-ups (owner, 2026-11-11; `server/utils/usernameRules.js`, checked first in `signUp`, before the profanity filter and any DB read): 3-20 characters of ASCII letters, digits, space, `_ - .`; starts with a letter or digit; no space at either end (iOS 1.1.0 sends the field as typed, web trims), no double space; no emoji, which also keeps humans off every bot name (bots are always `🤖 <persona>` / `🤖 Bot N`). Each refusal is its own `signUpResponse {success:false, message}` (web: toast "Registration failed: <message>", iOS 1.1.0: red text under the fields); Joi stays at 1-50 so a long name gets the rule message, not a validation error. Taken = an existing user ignoring case and whitespace around the stored name (`findNameClash`: exact `findOne` first, so a merged tombstone keeps its redirect, then an anchored, escaped `$regex` with `i`; no index, no migration, stored names never rewritten): "That name is taken." / `That name is taken: "Alan T" already exists, and capital letters don't make a different name.` Sign-up budget, per socket: the wrapper's `rateLimiter.signUp` (20 / 5 min, `serverError {code:'rateLimit'}`) counts every attempt; refusals by these rules, the profanity filter and the taken check spend only that, and only an attempt past them (bcrypt hash + insert) also spends `signUpAccount` (3 / 5 min, checked in-handler; over it `signUpResponse` "Too many sign-up attempts..."), so trying names never locks a player out. Existing accounts keep their names (including ones these rules refuse) and sign-in, restoreSession, profile lookups and merges stay exact. Tests: `server/socket/__tests__/signUpNames.test.js`, realMongo (b)

## Password hashing

- Password hashing (`server/utils/passwordHash.js`): bcryptjs (same `$2a$`/`$2b$` cost-10 format, no migration) in a `worker_threads` pool (`BAB_HASH_WORKERS`, default 2; lazy, unref'd while idle; >50 pending → `HASH_BUSY` → "Server is busy"; a crashed worker's jobs re-run inline). Inline bcryptjs when the Worker constructor throws and under Jest unless `BAB_HASH_POOL=1` (`server/utils/__tests__/passwordHash.test.js`). The CLIs (`setPassword`) keep plain bcryptjs

## Failed-sign-in throttle

- Failed-sign-in throttle (`server/socket/signInThrottle.js`): failures only (unknown user, wrong password; not merged-account redirects, DB errors or HASH_BUSY), 15 min sliding window: (ip, username) pair 10, ip 50, username 30 (pair and ip skipped when the IP is unknown); a success clears the pair; an (ip, username) that signed in or restored a session in the last 30 days is known-good and skips the username key (an outsider's guesses cannot lock out the household); a flood never evicts a key at its limit (a map full of lockouts fails closed for new keys); checked before any DB read and answered with the usual `signInResponse` failure. The pair/username keys are reserved synchronously with the check (no overshoot from parallel guesses); the ip key counts confirmed failures only (a family signing in together behind one NAT never blocks itself). restoreSession/rejoinGame/signUp are never limited. Client IP (`server/utils/clientIp.js`, `socket.data.clientIp` at connection): a public handshake peer is used as-is (headers ignored); behind a proxy/private peer (Railway's edge is in 100/8) `X-Real-IP` when it is a non-proxy IP that appears in `X-Forwarded-For` (or XFF is absent); the leftmost XFF entry alone is never trusted; else null and only the username key applies (never one shared key). Every password sign-in logs 'Sign-in client address' (peer, X-Real-IP, XFF, chosen ip): check it after a deploy that different networks get different IPs
