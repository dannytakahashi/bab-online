# Voice: signaling, TURN and web keys

Never auto-loaded: open it for `server/socket/voiceHandlers.js`, `server/voice/` (incl. `gameVoice.js`), `client/src/voice/` (including the `voiceHotkeys.js` overlay / mute keys), `client/src/ui/components/VoiceChatUI.js` or the iOS `Voice/` code.

## Voice signaling

- Voice signaling (`server/socket/voiceHandlers.js`; roadmap 30's security part, 2026-11-11): voiceOffer / voiceAnswer / voiceIceCandidate are forwarded only when the target is a connected socket id (`io.sockets.sockets`; never a room such as 'mainRoom' or `game:<id>`, never the sender), both sockets are signed in and in the same voice room (`gameVoice.voiceRoomOf`: a lobby (`playerLobbies`), a game (`playerGames`: entrants, seat owners incl. a lazy owner's socket), or, in a casual game, an admitted voice spectator (`game.voiceSpectators`, Spectator voice below)) — the peers voicePeerList/voicePeerJoined announce; any other pure spectator is refused (a legacy client never starts voice for one) — and neither user blocked the other (`socket.data.blockedUsers`, set by `rememberBlockList` at signIn / restoreSession / signUp / rejoinGame's session-token check and on every blockListUpdated success; a CLI merge is seen at the next sign-in; each side is checked against its own list; a signed-in socket with no list fails closed, refused both ways while `loadBlockList` reads it, with a warning). Per-socket limits checked in-handler (`rateLimiter.limits`: offer/answer 60, ICE 600 per 10 s since 2026-11-16, for a mesh of up to 8 people: 7 peers each; estimates, not measured with TURN), then the payload's Joi schema (`validators.schemas.voiceOffer` etc., V1_REMOVALS #18; the contract's `joiInHandler`: target id <= 64, SDP type + sdp <= 64 KB, candidate fields bounded, nulls and iOS 1.1.0's "" allowed); every refusal is dropped silently (debug log; no reply, never `serverError`, which would toast). A successful `blockUser` between two users who share a voice room (lobby, players, spectators) ends their call: each socket gets a private voicePeerLeft for the other (`gameVoice.endBlockedCall`; before 2026-11-16 an established P2P stream survived a block). Tests: `server/socket/__tests__/voiceSignaling.test.js`, `spectatorVoice.test.js`

## Play again voice

- At the end of a lobby-born casual game (`server/socket/playAgain.js`; server/CLAUDE.md, Lobby seats, "Play again"): the members moved back into the lobby (R, in row order) keep their calls (pairs within R are never sent anything; each r_i gets `voicePeerList` of the r_j before it and each such r_j a `voicePeerJoined`, which a client skips when already connected; a missing pair gets one offer, from the later one). Every other socket of the game's voice room at the end (main-room voice spectators, owners not moved) drops its calls with R (private voicePeerLeft both ways), except a legacy seat owner still on the score screen: its calls with R linger (as today's score-screen calls do) until it leaves that screen (joinMainRoom, createLobby, joinLobby, joinAsSpectator, the tournament entry points, a disconnect) or the lobby starts or goes, then private voicePeerLeft both ways. A moved member still on its results when the others start the next game without it (unsettled: it has not sent lobbyReturnSeen nor acted in the lobby) is not made an extra: leftLobby, and private voicePeerLeft both ways with the table, the extras and the others left out (`playAgain.leftOnResults`), so it never hears the next game. `voiceRoomOf` / `authorize` are unchanged: moved members are mapped lobby members, holds have no socket, and a lingering socket shares no room with R (an ICE restart between them is refused, as on today's score screen after `_retire`); a block ends a lingering call too (`gameVoice.endBlockedCall` asks `playAgain.isLingeringPair`). Shipped iOS builds only drop the peer on a private voicePeerLeft.
- Play again, web client (2026-11-16; `docs/claude/web-client.md`, Play again): the score modal keeps the game's voice session running (nothing stops it at gameEnd), so the moved members' calls carry on while each looks at the results; the server's voicePeerList / voicePeerJoined / voicePeerLeft at the return tick are handled as anywhere (an existing peer is skipped). lobbyReturn itself drops the table's voice settings while the modal stays (`endTableVoiceRules`). Return to Lobby keeps voice (`EXIT.LOBBY_RETURN`: no `stopVoice`), muted again (the same call; the next game starts muted, review 2026-11-18) and redraws the controls in the lobby header; the re-entry's voicePeerList skips the peers already connected. Return to Lobby also sends `lobbyReturnSeen` (as iOS does at its entry). The reopened lobby starting its next game while this player is still on the modal (it has not tapped Return, so the server counts it unsettled): `playAgain.leftOnResults` sends it leftLobby and ends its calls with the table and the extras (private voicePeerLeft both ways), so it never hears the next game; the modal stays and its voice session runs on with no calls until Return (to the main room) stops it. A spectatorJoined at the modal (a server that makes such a member an extra) still stops voice with a toast saying so.

## Voice TURN

- Voice TURN (owner, 2026-11-11: Cloudflare Realtime TURN, the PCM relay dropped): `getVoiceIceServers {requestId?}` (Joi, wrapper limit 20/min) → `voiceIceServers {iceServers, turn, expiresInSec, requestId?}` to the socket (`voiceHandlers.getVoiceIceServers`, `server/voice/turnCredentials.js`). Only a signed-in socket in a voice room (a lobby, a game, or an admitted voice spectator: `gameVoice.voiceRoomOf`) gets TURN (no new exposure: a lone lobby creator always got it); everyone else and every failure get the old Google STUN pair (`turn:false, expiresInSec:null`). Minting: `POST {base}/v1/turn/keys/{CLOUDFLARE_TURN_KEY_ID}/credentials/generate-ice-servers`, `Authorization: Bearer {CLOUDFLARE_TURN_API_TOKEN}`, `{ttl: 14400}` (4 h), 2.5 s timeout (AbortController), port-53 URLs dropped, body sanitized; cached in memory per username while ≥ 1 h is left, single flight per user, 60 s backoff after a failure, at most 120 mints per minute per process. Env unset = STUN only (voice as before). `CLOUDFLARE_TURN_API_BASE` points at a fake Cloudflare outside production only (ignored with a warning when NODE_ENV=production). Never log the token, the key id or a credential (failures log only the HTTP status or timeout/network). Web (`client/src/voice/VoiceChatManager.js`): `initialize` asks in parallel with the mic prompt and waits ≤ 4 s (else STUN); a TURN answer is reused per username for the tab and refreshed 30 min before expiry (`setConfiguration` on open connections), a STUN-only answer (the server's on any failure/backoff/unset env, or the 4 s fallback) is never kept, so each voice start and each restart ask again. A failed connection (`failed`, or not connected within 20 s: with no candidate pair Chromium never reports failed) gets one restart (the peer with the lower socket id refreshes the ICE servers and offers again on a new connection; the other refreshes too and waits 15 s for it), then the peer shows "voice unavailable" in the voice overlay (`isUnavailable`, `.voice-row__unavailable`); a later offer from it retries. No PCM relay any more (no ScriptProcessor, no `voiceRelayAudio` listener or emit); the server's handler, rate-limit key, Joi schema, both schema entries and the web constants went a day after the deploy (`contract/V1_REMOVALS.md` #20, done 2026-11-12): a `voiceRelayAudio` packet reaches no handler. iOS 1.1.0 is still STUN only; iOS 1.2.0 asks the same way (`Voice/IceServerStore.swift`: parallel with the mic prompt, 4 s, TURN reused per username and refreshed 30 min before expiry, one restart then "voice unavailable", 20 s connect timeout; V1_REMOVALS "iOS TURN"). Tests: `server/socket/__tests__/voiceIceServers.test.js`, `client/src/voice/VoiceChatManager.test.js`

## iOS sounds and voice

- Sounds never block the main thread (owner 2026-11-18: on build 15, an iPhone Air with voice on froze the table about 1 s at every sound: a card played, the others' cards, the draw, the deal; sounds off made it smooth, the web was smooth throughout). While voice runs, `SoundPlayer.prepareSession` returns before reading `AVAudioSession` at all (a getter is a synchronous call into the audio server, which WebRTC keeps busy), and every `AVAudioPlayer` call (the pool's `play`, the bid clock tune's start, volume and stop) runs on the serial `SoundQueue`, so a slow start delays only its own sound. The tune's time left is kept on main (`AudioTuneOutput.endsAt`), never read from a player still starting on the queue. A step that takes 100 ms or more (`category read`, `preload`, `play`, `tune play`) is reported once per launch (clientError kind `soundStall`, with the milliseconds and whether voice was on), so a device shows which step stalled. Tests: `SoundEffectsTests.testASoundDuringVoiceNeverReadsTheSession`.

Mute stays `isEnabled`, independent of the level. `setRemoteTrack` applies the stored mute and volume to a new track (first connect or a restart; before, a restart's track came up unmuted while the row still showed muted). Fixture `-uiVoicePanel YES`; tests `LobbyParityTests` (clamp, per-player store), `LobbyParityUITests.testEachPlayerHasAVolumeSlider`. Not yet heard on a device
- iOS table sounds and the audio session (2026-11-15; ships with the next iOS build, after 1.2.1 build 9): `VoiceChatManager.configureAudioSession` sets playAndRecord / voiceChat (`.defaultToSpeaker`, `.allowBluetoothHFP`) before `isActive` goes true, synchronously on the main actor, and `shutdown` deactivates the session (`.notifyOthersOnDeactivation`) without resetting the category (both through `VoiceAudioSession` since 2026-11-17: next bullet). `SoundPlayer` (main actor) never sets the session while `VoiceChatManager.shared.isActive`: a sound then plays through voice's session (the silent switch does not mute it; not yet heard on a device). With voice off, right before each sound, any category but `.ambient` (the launch default soloAmbient, which would stop the user's music, or the playAndRecord voice left behind) is set to `.ambient`, which respects the silent switch and mixes with other audio (if that

- iOS voice on the loudspeaker (owner 2026-11-17 on an iPhone Air: voice, spectating and probably playing, came only from the earpiece; `Voice/VoiceAudioSession.swift`). Cause, in WebRTC M140 (stasel/WebRTC 140.0.0, webrtc.googlesource.com `refs/branch-heads/7339`): when a call starts playout, `AudioDeviceIOS::InitPlayOrRecord` calls `RTCAudioSession configureWebRTCSession` (so does `UpdateAudioUnit`, but only when it initializes a unit it had uninitialized and unconfigured because `canPlayOrRecord` went false; `ConfigureAudioSession` returns early while `has_configured_session_` holds), which applies `RTCAudioSessionConfiguration.webRTCConfiguration`; its default `categoryOptions` is only `AllowBluetooth` (= `.allowBluetoothHFP`, no `DefaultToSpeaker`), and `setConfiguration` sets the category again whenever the options differ, so the app's `.defaultToSpeaker` was dropped the moment audio started and playAndRecord / voiceChat routed to the receiver. Fix: `VoiceAudioPolicy` holds the values (playAndRecord, voiceChat so the VoiceProcessingIO echo cancellation stays, `[.defaultToSpeaker, .allowBluetoothHFP]`); `VoiceAudioSession.installWebRTCConfiguration()` makes them WebRTC's configuration (`RTCAudioSessionConfiguration.setWebRTC`, WebRTC's sample rate / buffer / channels kept) in `makeFactory` before the default module exists, and again on every activation. `Hooks.live` goes through `VoiceAudioSession.shared` (`activate()` / `deactivate()`): category and activation through `RTCAudioSession` under its lock, so WebRTC's activation count includes ours (with raw AVAudioSession calls WebRTC held the only count and deactivated the session whenever its unit stopped, voice on or not). One activation is held and balanced (`activated`); WebRTC deactivates (`.notifyOthersOnDeactivation`) once both are released. Not `.allowBluetoothA2DP`: with HFP allowed iOS picks HFP on a device with both (AirPods), so A2DP would only add output-only Bluetooth speakers. Safety net while active: an `AVAudioSession.routeChangeNotification` observer (posted on AVAudioSession's thread, checked later on main from AVAudioSession's getters without the RTCAudioSession lock, which is taken only to force: WebRTC's worker holds that lock through `InitPlayOrRecord`'s whole audio unit set-up, when route changes cluster, and main would wait behind it) and a check right after activation force `.speaker` (`overrideOutputAudioPort`, through RTCAudioSession) only when every output is `.builtInReceiver` and no headset / Bluetooth / car / USB port is an available input (`VoiceAudioPolicy.shouldForceSpeaker(outputs:availableInputs:)`; someone who picked "iPhone" in the route picker with AirPods around keeps it). With the configuration fix it should never fire: it covers any path that drops `.defaultToSpeaker` again and logs `[Voice] route was the receiver, forced the speaker` so a device run shows whether it did. Paths checked in WebRTC's source: every `configureWebRTCSession` reads the installed values; after an interruption (a phone call, Siri) or app-did-become-active WebRTC only re-activates the session (`updateAudioSessionAfterEvent`, `setActive`; the unit is stopped and started again, or with the `WebRTC-Audio-iOS-Holding` field trial uninitialized and initialized again, never reconfigured, since `has_configured_session_` stays set), whose category and options are unchanged; a media services reset puts iOS's default category back and WebRTC again only re-activates, so `VoiceAudioSession` also observes `AVAudioSession.mediaServicesWereResetNotification` while active and sets voice's category, mode and options again on main (logs `[Voice] media services were reset, voice's category set again`; the audio unit itself is WebRTC's to recover); the category survives interruptions and backgrounding (the app does not touch the session there: `handleBackground` / `handleForeground` only switch the track); listen-only, talking, mute / unmute and re-offers do not touch the session; shutdown + initialize activates again with the same values; `SoundPlayer` never touches the session while voice is active and its `.ambient` after voice is replaced by the next `activate()`. Pacing (owner 2026-11-18: an iPhone Air on build 14, spectating with listen-only voice, ran hot and stuttered while the same table on the web was smooth; the simulator showed builds 13 and 14 idle at the same CPU, so the device-only route path is the suspect, unconfirmed): the net never answers a route change its own override caused (reason `.override`), forces at most once per 5 s (`SpeakerForceGate`), and after 3 forces within 30 s (the receiver keeps coming back: a fight with WebRTC) stops for the call, logs and reports once (clientError kind `voiceRoute`); separately, more than 20 route changes within 10 s while voice runs are reported once per launch with the reasons seen (`RouteChurnMeter`, kind `voiceRouteChurn`), so a loop on a device shows in the server log either way. Tests: `VoiceAudioSessionTests` (the values, WebRTC's stock options lacking `.defaultToSpeaker`, the installed configuration, the route table, the gate's pacing and give-up, the churn report). The real route can only be confirmed on a device: the simulator has no earpiece, and the unit tests never reach RTCAudioSession (silent hooks and `SilentAudioDevice`).

## iOS voice tests (no CoreAudio)

- No iOS unit test negotiates a call, starts playout or recording, or activates the audio session on WebRTC's default audio module (2026-11-16).
