# Voice: signaling, TURN and web keys

## Voice signaling

- Voice signaling (`server/socket/voiceHandlers.js`; roadmap 30's security part, 2026-11-11): voiceOffer / voiceAnswer / voiceIceCandidate are forwarded only when the target is a connected socket id (`io.sockets.sockets`; never a room such as 'mainRoom' or `game:<id>`, never the sender), both sockets are signed in and in the same voice room (`gameVoice.voiceRoomOf`: a lobby (`playerLobbies`), a game (`playerGames`: entrants, seat owners incl. a lazy owner's socket), or, in a casual game, an admitted voice spectator (`game.voiceSpectators`, Spectator voice below), or an admitted member of a tournament's voice room (`tournament:<id>`, Tournament voice below)) — the peers voicePeerList/voicePeerJoined announce; any other pure spectator is refused (a legacy client never starts voice for one) — and neither user blocked the other (`socket.data.blockedUsers`, set by `rememberBlockList` at signIn / restoreSession / signUp / rejoinGame's session-token check and on every blockListUpdated success; a CLI merge is seen at the next sign-in; each side is checked against its own list; a signed-in socket with no list fails closed, refused both ways while `loadBlockList` reads it, with a warning). Per-socket limits checked in-handler (`rateLimiter.limits`: offer/answer 120, ICE 1200 per 10 s since 2026-11-25, for the largest mesh a room may be, a tournament voice room at its ceiling of 20: 19 calls each, an entry burst plus a full ICE-restart round at ~30 candidates a call; before that 60 / 600 for 8 people; `voiceSignaling.test.js` ties them to `tournamentVoice.MAX_ROOM_MAX`; on loopback with STUN only a call sends 2 candidates (`scripts/voice-mesh-measure.mjs`), with TURN not measured yet), then the payload's Joi schema (`validators.schemas.voiceOffer` etc., V1_REMOVALS #18; the contract's `joiInHandler`: target id <= 64, SDP type + sdp <= 64 KB, candidate fields bounded, nulls and iOS 1.1.0's "" allowed); every refusal is dropped silently (debug log; no reply, never `serverError`, which would toast). A successful `blockUser` between two users who share a voice room (lobby, players, spectators) ends their call: each socket gets a private voicePeerLeft for the other (`gameVoice.endBlockedCall`; before 2026-11-16 an established P2P stream survived a block). Tests: `server/socket/__tests__/voiceSignaling.test.js`, `spectatorVoice.test.js`

## Session mute (owner 2026-11-19)

- Owner: "it defaults to muted now which is great, but when you return back to the lobby at the end of a game to play again it mutes you again - it shouldn't do that, once you unmute in a session it should stay unmuted". ## SFU voice (server)

Cloudflare Realtime SFU for the tournament voice room (owner 2026-11-26, after the spike: `spike/sfu/REPORT.md` on the local branch `spike/sfu`). Server PR 1: everything below is behind `VOICE_SFU` (default off) and no client sends `sfuVoice` yet; the web transport (PR 2) and the iOS transport (PR 3) follow "The client protocol" at the end of this section. Owner decisions: SFU for the tournament lobby room only, tables / lobbies / casual games stay on the peer-to-peer mesh; no fixed small cap on the SFU room ("worth having the capability for unbounded size"); the mesh at most 8 ("keep 8 as the direct limit"); an old client in an SFU room gets no voice there (PR 4 adds its "update to use voice in this room" note); privacy text (PR 5) and the rollout (PR 6) are later.

### Mode, caps and sizes

- Flag (`server/voice/sfu/config.js`, every value read at call time): `VOICE_SFU=off|tournament` (anything else off, one warning). With `tournament` AND the Cloudflare app configured (`CF_SFU_APP_ID`, `CF_SFU_APP_SECRET`; the same names as `~/.bab-secrets/cf-sfu-dev.env`; `CF_SFU_API_BASE` points at a fake Cloudflare outside production only) a tournament's voice room is an SFU room. The flag on without the app: the room stays a mesh (one warning). Startup logs `Voice SFU {flag, appConfigured, roomMax, graceMs}`, never the id or secret.
- A room's transport is decided when its first member enters (`tournamentVoice.settleMode`, `t.voiceRoom.mode` 'mesh' | 'sfu') and kept while anyone is in it (members or SFU members still in their reconnect grace); an empty room takes the flag again at its next entry. So no live room switches transport inside a process. `voiceRoom` is never saved, so after a deploy the new process decides again from its own flag: a client must handle the room it gets (an `sfuRoster` = SFU, otherwise the mesh lists as today).
- Mesh cap (`tournamentVoice.meshMax`): flag off = `TOURNAMENT_VOICE_MAX` (default 20) exactly as before; flag on = at most 8 (`MESH_MAX_WITH_SFU`), which with the flag on only applies when the app is not configured. Tables (4) and family lobbies (8) were already within 8. Not changed while the flag is off (production behaviour); whether the kill switch (flag back to off) should also drop the mesh to 8 is PR 6's call.
- Who gets SFU voice: a member of the room (`tournamentVoice.enter`: the cap `tournamentVoice`, on the lobby screen) whose clientHello carried `sfuVoice` (recorded per member at entry, `member.sfu`). A member without it is in the room's record (the tournament's own presence is unchanged) and gets nothing at all in an SFU room: no `voicePeerList` / `voicePeerJoined` / `voicePeerLeft`, no `tournamentVoiceStatus`, no `sfuRoster`, and every `sfu*` request answers `not_in_room`. `change()` in an SFU room mutates the record and hands it to `sfuRoom.sync`; no mesh event is ever emitted there (`sfuVoice.test.js` "the mesh is never in an SFU room"). `gameVoice.voiceRoomOf` gives an SFU member `sfu:<tournamentId>`: `voiceHandlers.authorize` refuses every mesh offer / answer / candidate there (`sfu_room`), `getVoiceIceServers` still gives it TURN.
- Safety ceiling: `VOICE_SFU_ROOM_MAX`, default 100, clamped 2..100000 (no fixed small cap, owner 2026-11-26: "worth having the capability for unbounded size"; the code maximum is only there so a typo cannot make it 0 or negative, and the default 100 is the owner's to confirm). Past it the SFU-capable members wait in line (`sfuRoster {status: 'waiting', cap}`), and the first in line is admitted when one leaves. Why 100 (no participant limit is documented): it bounds the server's own fan-out (each roster change is one `sfuMember` per member, so a full room's churn is O(N) per event and O(N^2) for a whole room re-entering after a deploy: 10,000 emits at 100), the SDP a session carries (below), a phone decoding that many streams if everyone talks, and the egress bill (each publisher costs one stream per listener: 100 members with 10 talkers = 990 streams, about 54 Mbps of egress at ~55 kbps a stream on the wire, about $1.2 an hour at $0.05 / GB after the free TB; muted members cost nothing). Raise it with the env once a real big room has been measured.
- Cloudflare's documented limits (developers.cloudflare.com/realtime/sfu/platform/limits/, read 2026-11-26): 50 API requests per second per session (not per app); at most 64 tracks per request; no fixed upper bound on tracks per session ("endpoint and connection capacity set practical limits"); a track with no incoming media for 30 s is garbage-collected; a 30 s session / track reuse window after lost connectivity; operations that need a transport wait up to 5 s for it. Not documented: a maximum number of sessions, participants or tracks per room, or any SDP size limit. Measured here (live, 2026-11-26, `scripts/voice-sfu-smoke.mjs`): each pulled track adds one m-section, about 660 bytes to the SFU's offer and 570 to the client's answer (1 to 14 m-sections: 1.3 to 9.9 KB offers), so 100 pulled tracks is about 66 KB per offer; the Joi bound on an SFU session description is 256 KB (`validators.MAX_SFU_SDP_LENGTH`), Socket.IO's default message limit 1 MB. Cloudflare lets one session pull the same track again and again (14 pulls of one track answered), so the server refuses a pull of a track the session already pulls or is asking for (`duplicate`, across asks too) and, as a backstop, caps a session's open pulls at the ceiling (`too_many_pulls`). Session ids are 64 hex characters; mids are decimal and reused after a close. Not measured: the 50 requests a second limit, a room above 3 people live (the spike ran 20 on web), and how long a listen-only session that pushes nothing stays alive.

### The server side

- `server/voice/sfu/cloudflareClient.js`: the only code with the secret (the Bearer header; never logged, never sent). `newSession`, `push` (local tracks + our offer), `pull` (remote tracks, no SDP), `renegotiate` (our answer), `close` (negotiated with an offer, or `force: true`), `iceRestart` (the undocumented form the spike found: `POST tracks/new` with the iceRestart offer re-declaring our own local track, same mid and trackName; `PUT renegotiate` with an offer answers 406, `tracks/new` with no tracks 406), `getSession`. Each resolves `{ok, status, body, error, ms}`; `error.code`: `session_gone` (HTTP 410, Cloudflare's `session_error`), `timeout` (`VOICE_SFU_TIMEOUT_MS`, default 8 s, above Cloudflare's own 5 s wait so a dead session answers 410 first: measured 5.15-5.17 s), `network`, `cloudflare_error` (status + Cloudflare's errorCode; retryable for 406 / 409 / 429 / 5xx), `bad_response`, `unavailable`. A 200 with failed tracks is not an error: each `tracks[i].errorCode` is passed on.
- `server/voice/sfu/sessionQueue.js`: one serial queue per session (Cloudflare: serialize mutations per session; a second `tracks/new` before the previous exchange completed can answer 406), at most 16 client jobs (`busy` past it), and a client job that has not started within 3 s (`WAIT_MS`) answers `busy` then and is never sent (so a reply always comes within about 11 s: 3 s plus one 8 s Cloudflare call, and an ask a client gave up on never reaches Cloudflare later); `drop(key, reason)` answers every client job not started (a replaced session's queued work answers `superseded`, a 410'd one's `session_gone`), so a ~5 s 410 call never holds the new session's work (the spike's churn bug). A job re-checks that the session is still the caller's when its turn comes and after Cloudflare answered (`superseded` otherwise). Session creation queues per member. The server's own work (the revocation and block closes below) runs on the same queues as `internal` jobs: no deadline, no depth limit, kept by `drop`.
- `server/voice/sfu/sfuRoom.js`, the roster, per username in `t.voiceRoom.sfu.entries` (socket-keyed membership stays tournamentVoice's): `{socketId, sessionId, sessionSocket, trackName, localMid, pulls}`. `state` is `reconnecting` while the member has a session its current socket has not created or resumed (it dropped, came back on a new socket, or the server restarted), else `live`. A member that drops WITH a session stays listed as reconnecting for `VOICE_SFU_GRACE_MS` (default 38 s: Cloudflare keeps a session about 30-35 s); past the grace its session is cleared (`sfuMember session` with sessionId null) and, still away, it is `left`. Back within the grace on any socket (a reattach, a lobby-phase re-join) it is listed again as reconnecting until it resumes (`sfuResume`) or makes a new session. A member without a session that drops just leaves (nothing to keep). Leaving the room any other way (seated at a round's table, leaveTournament, the main room, a lobby, spectating) removes it at once: `left` to the rest, `sfuRoster {status: 'out'}` to it; `cancelTournament` and the results window's end close the room (everyone `out`, nobody kept as reconnecting, one stats line).
- Revocation (review of #433): only the server can stop a session from hearing the room (an honest client closes its own pulls; a modified one need not, and in the mesh each publisher closed its own connection to someone who left). Whenever the server stops holding a member's session (it left the room in any of the ways above, the room closed, a new `sfuSession` or a resume of another session replaced it, the grace ran out, `sfuLeave`), it queues on that session `GET sessions/{sid}` and a `tracks/close` with `force: true` of every remote track listed (the record of pulls is the fallback when the GET fails; a 410 needs nothing), logged `Voice SFU: pulls revoked {why, tracks, ok}`; and it remembers the session id as ended in the room, so an `sfuResume` of it answers `session_gone`. A pull Cloudflare answered after its asker lost the session (left, replaced it, or its socket dropped while the call ran) is answered `superseded` and its new mids are closed by force too (`Voice SFU: late pulls closed`). A member's last 4 session ids stay in `entry.recent` for the block close.
- Session ownership across a restart (`server/voice/sfu/sessionToken.js`): `sfuSession` answers a `sessionToken` = base64url HMAC-SHA256 over `sfu1|<tournamentId>|<username>|<sessionId>` with a key derived from the app secret, so any instance with the same secret verifies it (`sfuResume` with another member's session or a forged token: `bad_token`); never logged.
- Blocks: each entry keeps its member's block list by username (`entry.blocks`: copied from its socket at entry, kept current from ANY socket of the user by `voiceHandlers.rememberBlockList` -> `sfuRoom.blockListChanged`, so a member away in its grace, with no socket, still has one; loaded from the user document when missing). A pair where either list is unknown counts as blocked (fail closed, as the mesh's `blockedBy`). A blocked pair never sees each other in `sfuRoster` / `sfuMember` and their pulls are refused (`blocked`). A list change (`blockUser` / `unblockUser`, a rename, a lookup that completes) is applied per pair: a new block sends each an `sfuMember left` for the other (a member who is away just gets nothing) and `BLOCK_ENFORCE_MS` (5 s) later the server closes their pulls of each other at Cloudflare by force, worked out when the job runs from Cloudflare's own list (`GET` of each session of one, current, recent or at the block, then every remote track whose source is a session of the other), never from a username stored with a pull (unknown for a pull re-registered before its publisher resumed after a restart); an unblock, or an unknown list that loads, sends each the other's record as `joined`. An `sfuResume` that lists a pull of someone it is blocked with gets that pull closed by force at once. `gameVoice.endBlockedCall` -> `sfuRoom.blockedPairFound` only reports that the pair shared the room.
- Pulls are checked per track: only another member's CURRENT published track (`sessionId` + `trackName` as the roster has it) in the same SFU room; refused per track as `not_in_room` (anything else: another tournament's, an old session, a member not publishing), `own_track`, `blocked`, `duplicate` (twice in one ask, a track the session pulls already: `errorDescription` 'already pulled as mid N', or one whose pull is still being asked), `too_many_pulls`; a pull with nothing allowed makes no Cloudflare call.
- Limits (`rateLimiter.limits`, checked in the handler, answered `rate_limited` with `retryAfterMs`): `sfuSession` 6 a minute; `sfuCall` 300 per 10 s for every other op together (a member's join cost to the others is a pull + a renegotiate each; 100 publishers joining with no client batching is ~200 calls; under Cloudflare's 50 / s per session).
- Metrics and logs (no secret, token, SDP or body anywhere; `sfuVoice.test.js` checks): one `Voice SFU: Cloudflare call` debug line per call (op, status, ms, per-track error codes), `Voice SFU: Cloudflare call failed` (warn; info for a 410) with op / status / code / Cloudflare's code / ms; `Voice SFU: session created` / `session resumed` / `reconnect grace over` / `room full` / `pulls revoked` / `late pulls closed` / `blocked pair kept apart` / `blocked pair pulls closed by force` (info); and per room `Voice SFU: room stats` every 60 s while it changed, at its close and at a shutdown or handoff (`utils/shutdown.js` -> `sfuRoom.logAllStats('shutdown')`): members, publishing, open pulls, calls, errors, 410s, timeouts, sessions, pushes, pulls, pull errors, refused tracks, calls by op.

### The wire (contract/src, `$defs.sfu*`; listed for the web's constants, excluded from Swift until PR 3)

- c2s, status `unsent` (`sentBy` nobody) until a client sends them; each carries a `requestId` (1-64 chars) and is answered by exactly ONE private `sfuReply {requestId, op, ok, ...}`; a payload without a usable requestId is dropped silently (debug log), everything else that is refused is an `sfuReply ok: false` (never `serverError`): `sfuSession {}` -> `{sessionId, sessionToken}`; `sfuPush {sessionId, offer, mid, trackName}` -> `{answer, tracks}`; `sfuPull {sessionId, tracks: [{sessionId, trackName}] (1..64)}` -> `{requiresImmediateRenegotiation, offer|null, tracks: [{username, sessionId, trackName, mid|null, errorCode|null, errorDescription|null}]}`; `sfuRenegotiate {sessionId, answer}` -> `{}`; `sfuClose {sessionId, mids (1..64), offer?, force?}` -> `{answer|null, tracks}` (the offer is required unless force); `sfuIceRestart {sessionId, offer}` -> `{answer, tracks}`; `sfuResume {sessionId, sessionToken, trackName|null, mid|null, pulls?: [{mid, sessionId, trackName}]}` -> `{}` (`session_gone` for a session this process ended); `sfuLeave {sessionId?}` -> `{}` (idempotent).
- `sfuReply` error: `{code, retryable, retryAfterMs|null, status|null, cfCode|null}`, codes: `invalid`, `rate_limited`, `not_in_room`, `not_your_session`, `already_published`, `no_local_track`, `bad_token`, `busy`, `superseded`, `session_gone`, `timeout`, `cloudflare_unreachable`, `cloudflare_error`, `unavailable`, `server_error`.
- `sfuRoster {tournamentId, bootId, rev, status: admitted|waiting|out, cap, graceMs, self: {sessionId, trackName, state}|null, members: [{username, sessionId|null, trackName|null, state: live|reconnecting}]}`: to one socket when it enters the room, comes back on a new socket, draws its lobby again (a re-sent tournamentJoined), is let in from the line or put in it, or leaves (`out`).
- `sfuMember {tournamentId, bootId, rev, event, member}` to every other admitted member: `joined`, `session` (new session or none: sessionId null, trackName null), `published`, `unpublished`, `reconnecting`, `resumed`, `left`. `member` is the whole record (apply it as an upsert; `left` removes). Act on the record, not the event's name: after a restart a member comes back as `joined` (sessionId null) then `session` with the session it already had, and never `resumed`. `bootId` is `utils/instanceId.bootId` (one per process). `rev` grows per room.

### The client protocol (PRs 2 and 3 build to this)

1. **Caps and mode.** Send `sfuVoice` (with `tournamentVoice`) in clientHello. On the tournament lobby screen an `sfuRoster` means this room is an SFU room: use the SFU transport there and nothing of the mesh (the server sends no voicePeerList there). The server emits it in the same handler, synchronously right after `tournamentCreated` / `tournamentJoined` (only Cut for a buck's notes can come between), so decide on the next voice event, never on a timer: `sfuRoster` = SFU; `voicePeerList` / `voicePeerJoined` / `tournamentVoiceStatus` = the mesh exactly as today; nothing (alone in a mesh room) needs no voice yet (no voice alone), so wait. A mesh room while I still hold an SFU session (a deploy onto a process with the flag off): `pc.close()` first (no `sfuLeave`: it answers `not_in_room` there), then the mesh. The same on `tournamentLeft` or landing in the main room. `status: 'waiting'`: show "Voice is full (N people)" (N = `cap`), no voice; `'out'`: end the SFU session (no `sfuLeave` needed). Tables are always the mesh.
2. **Company and the start.** No voice alone: start only while the roster lists another member; muted at the start, as today. The session is lazy: call `sfuSession` only when there is something to pull (another member with a `trackName`) or on the first unmute. Keep `sessionId` and `sessionToken` in memory (a reload loses the PeerConnection anyway).
3. **One RTCPeerConnection per session**, `bundlePolicy: 'max-bundle'`, `iceServers: [{urls: 'stun:stun.cloudflare.com:3478'}]` (what the spike used; TURN from `getVoiceIceServers` may be added but is not measured with the SFU). No need to wait for ICE gathering (the SFU is ice-lite). Every request of a session goes through ONE client-side serial queue too; when the session is replaced, drop the old queue's pending work.
4. **Push on the first unmute, never before.** A muted-at-start member pushes nothing (an empty or silent sender breaks every pull of it: `empty_track_error`, then `not_found_track_error`). First unmute: `addTransceiver(micTrack, {direction: 'sendonly'})`, `createOffer`, `setLocalDescription`, `sfuPush {mid: transceiver.mid, trackName: 'mic'}`, `setRemoteDescription(answer)`; check `tracks[i].errorCode`. Later mutes: `track.enabled = false` (keeps sending silence, so the track stays pullable; no 30 s garbage collection). One track per session (another mid / name: `already_published`).
5. **Pull.** For every member whose `(sessionId, trackName)` you do not pull yet (from `sfuRoster.members` and each `sfuMember`): batch up to 64 per `sfuPull`; map each returned `mid` to its member BEFORE `setRemoteDescription(offer)` (ontrack fires inside it), `createAnswer`, `setLocalDescription`, `sfuRenegotiate`. Answer the offer whenever there is one, even when some tracks failed. Per track: `empty_track_error` / `not_found_track_error` (Cloudflare's: the publisher has no media yet, or it went) retry every 1 s up to 10 times; the server's `not_in_room` / `own_track` / `blocked` / `duplicate` / `too_many_pulls` / `no_result`: do not retry until the roster changes (`duplicate`: this session pulls that track already, or a pull of it is in flight; if you do not use that mid, `sfuClose` it first). The SDP grows ~1.2 KB (offer + answer) per pulled track.
6. **Close.** Compare each member's announced `(sessionId, trackName)` with the pull I HOLD for that username (not with the last roster value): equal, nothing to do (after a restart every resume announces `session` with the pair I already pull). A member `left`, its `trackName` became null, or its pair differs from my pull: close its pull (negotiated: `transceiver.stop()`, `createOffer`, `setLocalDescription`, `sfuClose {mids, offer}`, `setRemoteDescription(answer)`; on an error roll back and `sfuClose {mids, force: true}`), then pull its new track if any (one batch). Mids are reused by the SFU, so the SDP does not grow with churn. A member in `reconnecting`: KEEP its pull (it may come back on the same session; nothing to do when it `resumed`).
7. **Roster events.** Apply `sfuMember.member` as an upsert keyed by username (an unknown member = a join; `left` = remove). Within one socket events arrive in order after its `sfuRoster`; a new socket always gets a fresh `sfuRoster` first.
8. **Errors.** `session_gone` (410): the session is dead; never retry on it (each call on it costs ~5 s): close the PeerConnection, `sfuSession`, push again if unmuted, re-pull everyone (the server already told the room). `superseded`: the work belonged to a replaced session: drop it. `not_your_session`: this socket has not resumed that session: `sfuResume` or a new session. `not_in_room`: stop SFU voice until the next `sfuRoster`. `rate_limited` / `busy` / `timeout` / `cloudflare_unreachable` / retryable `cloudflare_error`: retry after `retryAfterMs` with backoff (0.5, 1, 2, 4 s). `invalid` / `bad_token` / `already_published` / `no_local_track` / `unavailable`: a bug or a state change: do not retry the same request. Wait at most ~12 s for any reply: a request that has not started within 3 s behind earlier calls answers `busy` without reaching Cloudflare, and a Cloudflare call times out at 8 s, so a reply comes within about 11 s. A reply that comes after I gave up: ignore it by requestId; the server closes anything a pull opened for a session I no longer hold.
9. **Media drops (the reconnect algorithm, `spike/sfu/reconnect/RECONNECT.md`).** Never act on the first `disconnected`: 5-12 s drops heal by themselves; start a 2 s timer and also react to the OS network-up event (web `online`, iOS `NWPathMonitor`). Recover when still disconnected after 2 s, on `failed`, on network-up or a downlink stall (next): if away under 25 s, the session was not 410'd and I have published a track: an ICE restart on the same session (`pc.restartIce()`, `createOffer({iceRestart: true})`, `setLocalDescription`, `sfuIceRestart`, `setRemoteDescription(answer)`, wait up to 6 s for connected; on an error roll back the offer; at most 2 tries); otherwise (away 25 s or more, a 410, 2 failed restarts, or a session that pushed nothing: `no_local_track`, since the restart form needs our own track) a new session. Measured live 2026-11-26: the ICE restart answered in 143-181 ms; the 410 came 45 s after the PeerConnection closed, after a 5.15 s wait. The ICE restart form is undocumented and not yet tried on iOS (PR 3 must confirm it; the fallback is a new session, 1.2-1.6 s instead of 0.3-0.5 s).
10. **Downlink stall detector.** Sample getStats every 200-500 ms; if connected, pulling at least one track and EVERY pulled track has received nothing for 2 s, run step 9 with force (an ICE restart though ICE says connected), at most once per 10 s (the NAT rebinding case: 11.7 s deaf without it, 2.9 s with it).
11. **Socket reconnect, same page / app process.** The new socket re-enters the room (the client re-sends joinTournament as today) and gets `sfuRoster` with `self.state: 'reconnecting'` and my old `sessionId`: if my PeerConnection is still alive (not `failed` / `closed`) send `sfuResume {sessionId, sessionToken, trackName, mid, pulls}` AT ONCE (do not wait for anything else; the others keep my pull meanwhile and hear me again with no re-pull), else a new session. The grace is `graceMs` (38 s) from the drop. `self.sessionId: null` with the SAME `bootId`: the server dropped my session (the grace ran out) and closed its pulls at Cloudflare: `pc.close()` and make a new session when needed (never `sfuResume` it: `session_gone`). The rule: a new `bootId` with `self.sessionId` null = resume (step 12); the same `bootId` with null = new.
12. **Server restart (a new `bootId`).** Only when the tournament survives the deploy (`LIVE_PERSIST=on` with an announced successor; docs/claude/server-infra.md): otherwise the tournament is gone, so on `tournamentLeft` or landing in the main room `pc.close()`. Media never stopped (sessions live at Cloudflare). The new roster has `self.sessionId: null`; the other members are missing from it, then arrive as `joined` with sessionId null, then as `session` with their old sessionId as each resumes: send `sfuResume` with the SAME session at once (never a new session for a signaling-only outage) and, for 20 s after seeing the new bootId, close no pull of a member who is missing or has a null session (they are re-registering; the server can hold a re-entry's joinTournament up to 8 s before an engine close); keep a pull whose `(sessionId, trackName)` comes back unchanged; after the 20 s apply the roster as usual.
13. **Leaving.** Voice stops on the screen (no company, the main room, a table, page hide / app terminate): `sfuLeave` (best effort; the room drops my track at once instead of after the grace, and the server closes my pulls), then `pc.close()`. Leaving the room any other way, the server closes my pulls at Cloudflare itself. Never on a socket drop (that is what the grace is for).
14. **Web specifics.** Chromium's audio service opens at most ~50 output streams per browser (the mesh harness hit it): past ~45 pulled tracks one `<audio>` element per track goes silent, so a big room should mix the pulls in one AudioContext (per-person volume and speaking detection through a GainNode / AnalyserNode per pull). Chrome sometimes shows a tiny extra inbound-rtp on a mid that survived a close: use the stream with the most bytes. Opus runs ~32 kbps per stream through the SFU against ~24 in the mesh; capping it (`maxaverage` / `setParameters`) cuts egress ~25% (not yet tried).

## Speaking levels at 20 and the over-cap notice (iOS 1.2.7)

- Why: the tournament room may go to `TOURNAMENT_VOICE_MAX` 20 once `MIN_IOS_BUILD` is 41 (owner 2026-11-25), so a 1.2.7 phone must carry 19 calls. Through 1.2.6 the speaking indicator asked every call for its whole stats report (`RTCPeerConnection.statistics`: every candidate pair, codec, transport, certificate) every 100 ms: 190 full reports a second at 19 calls. iOS cannot be fixed from the server later, so this ships in 1.2.7 (41).
- Now (`Voice/SpeakingPoll.swift`, `VoiceChatManager.pollSpeakingLevels`): each call is asked for its own audio receiver's stats only (`statistics(for: receiver)`, the spec selection: that receiver's inbound-rtp and what it references, a handful of objects); my own level from one call's sender (`statistics(for: sender)`: outbound-rtp and media-source). One request in flight per call (and one for mine): a call whose answer has not come is skipped that tick, and a closed call's entry is dropped (`closePeer`). The poll runs every 100 ms up to 8 calls and every 200 ms past 8 (`SpeakingPoll.interval`; the timer restarts itself when the call count crosses), the 400 ms hold is kept (two polls at the slower rate). The web is unchanged (its analyser path never read full reports).
- Over-cap notice: `ClientHello.caps` adds `tournamentVoiceStatus` (`TournamentVoice.statusCap`); `TournamentSocketHandler.handleVoiceStatus` keeps `TournamentState.voiceFullCap` (admitted false: the cap; admitted true: nil; only on the tournament lobby screen, the web's rule; cleared by a seat at a table (tournamentGameAssignment) and `reset`), and the tournament lobby's header shows "Voice is full (N people)" under the round line (`tournament.voiceFull`, the web's words, `TournamentVoice.fullNote`; hint "You'll join voice when someone leaves it."; announced once to VoiceOver when it first appears). Voice itself is untouched: a member in line has no company, so voice never starts.
- Tests: `TournamentExtrasTests` (the interval and the levels from fake stats, a real in-process call whose tone is seen as speaking through the per-receiver and per-sender stats with no whole report asked, nine calls slowing the poll and eight speeding it back up; the notice's handler and words; fault-injected: a broken level reader or settings handler fails them), `TournamentExtrasUITests` (`-uiVoiceFull 20`, `-uiVoiceAdmit <s>`, default size and AX5). Not checked: 19 real calls on a device (the 12 / 20 peer measurement is the server harness's, `npm run voice:measure`).

## iOS voice tests (no CoreAudio)

- No iOS unit test negotiates a call, starts playout or recording, or activates the audio session on WebRTC's default audio module (2026-11-16). One test still builds `VoiceChatManager.shared` (and so the default module) without starting a call: `LobbyParityTests.testAPlayersVolumeIsKeptPerPlayer`, which only stores volumes; with no track or call the VoiceProcessingIO unit is never initialised. Before, a test that negotiated real in-process WebRTC calls with audio tracks (`SpectatorVoiceManagerTests`, since build 16 `MutedStartVoiceTests`, and `PlayAgainTests`) sometimes aborted the whole unit run on a busy Mac (several simulators). WebRTC's default audio device module initialises its VoiceProcessingIO unit (`AudioDeviceIOS::InitPlayOrRecord`) as soon as a negotiated call starts playout, which needs no network. Against the simulator's audio HAL that call stalled until CoreAudio aborted the process: `HALSystem.cpp AudioObjectPropertiesChanged: no such object`, then `[default] Initialize: RPC timeout. Apparently deadlocked. Aborting now.`, then xcodebuild's "Restarting after unexpected exit, crash, or test timeout".
- The fix: `VoiceChatManager.init(hooks:iceStore:audioDevice:)` takes an optional `RTCAudioDevice`. With nil (the app, `shared`) the factory is still `RTCPeerConnectionFactory(encoderFactory:decoderFactory:)`, so the app keeps WebRTC's default module exactly as before. The tests pass `SilentAudioDevice` (`BABOnlineTests/Support/SilentVoice.swift`): every call returns YES, nothing is opened and no samples flow. WebRTC wraps it in its ObjC audio device adapter, so the audio unit, RTCAudioSession and AVAudioSession are never reached. Peer connections, offers / answers, transceiver directions, track enabled state, re-offers and mutes by username are still WebRTC's real ones.
- `Hooks` also gained `deactivateAudioSession`, which shutdown now calls for its `setActive(false)`. That call used to go straight to AVAudioSession, even in tests; `.live` now goes through `VoiceAudioSession` (the loudspeaker bullet above).
- Every test builds its managers with `VoiceChatManager.silent(requestRecordPermission:sendOffer:sendAnswer:audioDevice:)`: no-op audio hooks, a 50 ms ICE store and the silent device.
- Options not taken: `RTCAudioSession.useManualAudio = true` + `isAudioEnabled = false` (the default module still creates the VoiceProcessingIO unit and registers with the session, skipping only its Initialize, and it is global state the app would have to set under XCTest), and an XCTest check inside the manager (production code branching on the test host).
- Tests: `SilentVoiceTests`. A negotiated call starts playout on both silent devices, which shows WebRTC uses them. A source scan fails on any `VoiceChatManager(` in `BABOnlineTests` outside `SilentVoice.swift`, and on any test that starts `VoiceChatManager.shared`.
