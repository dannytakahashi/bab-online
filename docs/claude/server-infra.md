## Deploys, crashes and health

- Service settings are infrastructure as code: `.railway/railway.ts` (Railway's IaC, `railway/iac`; `railway.toml` config as code is deprecated and stops being read on 2026-12-01; removed here 2026-11-15). It is NOT applied on push: from a checkout linked to the project (`railway status` shows project beautiful-analysis, environment production) run `npm install --no-save railway@3.17.0` (the SDK the file imports; kept out of package.json so CI and production never install it), then `railway config plan` and, if the diff is what you meant, `railway config apply`. Variables are unmanaged (`variables: { managed: false }`): MONGO_URI, the TURN keys and PORT live only in the dashboard, never in this public repository. What it sets on the `bab-online` service:

  - deploy healthcheck `/ready`, timeout 120 s: a new deploy takes traffic only once `/ready` answers 200 (DB ping); one whose DB never connects within the timeout fails and is never switched to, so the old deploy keeps serving. 120 s covers connectDB's backoff on a slow Mongo (each attempt gives up after 5 s). Railway probes `$PORT`, from `healthcheck.railway.app`; the service variable `PORT=3000` (set 2026-11-15) matches the hard-coded `server.listen(3000)` and the domain's target port (babonline.io → 3000). Without it Railway injects 8080 and the probe fails every deploy: a `/health` healthcheck (53509f3) was pulled 25 minutes later in a646178 for that reason. index.js logs `PORT is N but the server listens on 3000` at boot if they ever differ again. First healthcheck-gated deploy: 2026-11-15, "[1/1] Healthcheck succeeded!"
  - restart policy: Railway's default, ON_FAILURE with 10 retries, so a crash (exit 1) is restarted and a deploy's SIGTERM (exit 0) is not. Not written in the file: Railway stores the default as null, and an explicit value shows as a change in every plan
  - domain babonline.io → port 3000, one replica in us-west2
  - `drainingSeconds: 20` (15 applied 2026-11-16, 20 applied 2026-11-18 ahead of deploy survival PR 5, owner approved; the plan showed Railway's value as null before the first, i.e. its default; the key is in the railway SDK 3.17.0 `DeployConfig` typings): the old deploy's time between SIGTERM and SIGKILL. The graceful shutdown below takes ~1.5 s (today's path) or up to 6.5 s to the socket close (the `LIVE_PERSIST=on` handoff) and is capped at 15 s (`HARD_EXIT_MS`, 10 s before deploy survival PR 5; 5 s under this), so it always finishes and exits with its own code; the new deploy already serves by then (healthcheck), so it delays nothing. The figures 20 / 15 / 6.5 s are pinned by `server/__tests__/drainBudget.test.js` (drainingSeconds read from `.railway/railway.ts`).
- Crash exits (`server/utils/shutdown.js`): SIGTERM/SIGINT exit 0 (a deploy's stop: no restart), `uncaughtException` exits 1 (Railway restarts it ON_FAILURE; before 2026-11-15 a crash exited 0 and the site stayed down until the next deploy). Both run the same graceful path: `server.close`, the deploy notice (`noticeGames`: every live game, spectators included, gets the system line "This game was interrupted by a server update. It won't count toward stats." in its game log ("server restart" instead on a crash, exit 1), as the existing `gameLogEntry` room broadcast, which web and iOS 1.2.0 already show as a log line; ended games skipped, a throwing game logged and the rest still told; `server/index.js` passes the GameManager's games), `serverShutdown {message}` to every socket, 1 s, `io.close`, the end-of-game writes still in flight (`trackInFlight`, at most `HARD_EXIT_MS` minus the fixed waits and a 1 s margin, 7.5 s; during the drain each retry waits at most 250 ms and retries go on until its deadline, `retryDelay` / `shutdownAllowsRetry`; logs 'Exiting with writes still in flight' if any are left), 0.5 s, exit; a hard deadline (`HARD_EXIT_MS`, 15 s since PR 5; today's path keeps its 7.5 s in-flight wait) exits with the same code if anything wedges, and a throw inside the shutdown still exits. A second reason while one is running forces the exit at once with the FIRST reason's code (a crash during a deploy's SIGTERM exits 0). `unhandledRejection` is logged only. With `LIVE_PERSIST=write` (Live game persistence, below) the store's `shutdown()` runs right after `serverShutdown`: this process's live docs are deleted (bounded at 2 s, drained like an in-flight write); off, `server/index.js` passes no `persist` and nothing changes. With `LIVE_PERSIST=on` running as 'on' (the unique gameId index; else today's write path) `server/index.js` also passes `handoff` (`server/game/persist/handoff.js`) and the shutdown is, in this order: `server.close`; `serverShutdown` to every socket at t=0 (as today: clients show "Restarting for an update…", iOS starts its 8 s disconnect wait); a `socket.use` gate drops every client event from then on; the handoff: (1) settle, 0.5 s: the sweep stops (resolve answers 'pending', the pointer clears skip), the instance doc says `shuttingDown`, every writer's op and every adoption in flight is awaited; (2) freeze, synchronous: each casual table is serialized, the writers are closed (the heartbeat beats on until the handoff ends), the table frozen and detached (so `io.close`'s disconnects find no seat); (3) the successor check, 1 s, BEFORE any release: a fresh (beatAt within 15 s) `serverInstances` doc with mode 'on', a later startedAt, another bootId, not shutting down; (4a) a read that finds none (or an 'off' / 'write' one): `deleteMany {owner: me}` on both collections, 2 s, never a release; (4b) one, or the read failed or timed out (a Mongo blip at SIGTERM is not "no successor": as below, but every saved doc whose final write did not land is released as it is, only a table serialize refuses (tainted, invalid) is deleted, and every table with a doc gets UNKNOWN): per table the final write (`replaceOne {_id, owner: me, released: false, rev: {$lt: its rev}}` at the next rev, still unreleased, so a routine update still in flight past the settle bound can never land over it; `insertOne` for a table never written), cut at 3 s, then ONE release `updateMany` for exactly the acknowledged ids, the saved docs of tables the holder self-fence had suspended (released as they are, outcome UNKNOWN: serialize refuses a suspended game, but it took no input or timer since) plus this process's ENDED tombstones (`released, releasedAt, releaseKind: 'handoff'`) in parallel with the delete of every other doc it owns, all within 4 s (both deletes skip ids whose adoption is still settling: a claim that lands after the store closed is released straight back by adopt.js, never deleted); then (5) one game-log line per table matching what was acknowledged: CONTINUE "The server is updating. This game will continue in a few seconds." (released), ENDED = today's line (its doc is gone, or it never had one: pre-deal, tainted), UNKNOWN "This game was interrupted by a server update. If it isn't back in a few seconds, it won't count toward stats." (a release or delete not acknowledged, an insert that may still land: the doc may be adopted after the stale-owner wait); a frozen table's line is the next seq and not stored; (6) `NOTICE_MS`, `io.close` (by 6.5 s), the in-flight drain (7 s at most), `SETTLE_MS`, exit 0. Tournament tables and the ambient demo game are not handed off in PR 5 (today's line, their docs deleted). A crash (`uncaughtException`) in 'on': never serialize; the writers close first (no notice is ever saved), each casual table is frozen and detached (each in try/catch), ONE `updateMany {owner: me}` releases every game doc (`releaseKind: 'crash'`, 2 s), then "The server hit an error and is restarting. This game should continue in a moment, possibly a move earlier." if acknowledged, else "This game was interrupted by a server restart. If it isn't back in a moment, it won't count toward stats.", and today's crash line for tables with no doc; exit 1. With no live table the handoff adds no wait (microtask-only). ## Live game persistence (deploy survival)

Deploy survival PR 4 (2026-11-17; the plan: PRs 5-6 add the handoff, adoption and resume). `server/game/persist/liveStore.js` (`getLiveStore()`: one per process, from `LIVE_PERSIST` at boot and the process `bootId`, `server/utils/instanceId.js`), the codecs `gameCodec.js` / `tournamentCodec.js` (what is saved), `hooks.js` (how game code reports a change).

- Modes: **off** (default): nothing runs (no hook listens, track / claim / scrub are no-ops; `/health` still shows the `persist` block). **write**: live games and tournaments are written while they run, tombstoned and deleted; a `serverInstances` doc with a 3 s heartbeat; no sweep, no adoption, no handoff, no new notice; at SIGTERM / a crash, after today's notice, the process deletes its own docs. **on** (PR 5, casual games): with gameRecords' UNIQUE gameId index (read at `start()`; without it exactly write, `effectiveMode` 'write' and one "LIVE_PERSIST=on runs as 'write'" log line) everything write does, plus: nothing is written before `start()` (its instance doc first); a casual game's doc says `ownerMode: 'on'` (adoptable; a tournament and its tables stay 'write' until PR 6); a lost casual (ownerMode 'on') doc is a fence (a lost 'write' doc, a tournament or its table, stops saving and plays on as in write mode: nothing adopts it); its routine updates are rev-monotonic (`rev: {$lt: newRev}` in the filter); the SIGTERM handoff and crash release (Deploys, above); the adoption sweep and `resolve()`; the holder self-fence. See "'on': adoption, resolve, liveness" below
- Collections (`server/database.js` getters; `ensureIndexes` builds the indexes whatever the mode, skipping a collection a caller did not pass, as `scripts/restore-db.js` does):
  - `liveGames` `{_id: gameId, v, kind: 'live'|'ended', owner: bootId, ownerMode, released, releasedAt, rev, createdAt, updatedAt, expireAt, adoptAttempts, adoptedBy, adoptedAt, stage, tournamentId, state, log, logTotal, bots, ended?}`: indexes `released_1`, `owner_1`, TTL `expireAt_1` (0 s)
  - `liveTournaments` the same envelope with `phase, state, completedAt` (no log, ended): the same indexes plus `state.players.username_1`
  - `serverInstances` `{_id: bootId, deploymentId, mode, startedAt, beatAt, beatSeq, shuttingDown, gameIds, tournamentIds}`: TTL `beatAt_1` (1 day); the ids are rewritten on every beat and `$addToSet` when a game or tournament is created
- TTLs: `expireAt` = the game's / tournament's `createdAt` + 24 h ("always within a day"); the store stops writing an entity, and deletes its doc, at `createdAt` + 23 h 50 m, so the TTL never deletes a doc it still writes (the game plays on unsaved)
- The bid clock is NOT saved (`game.bidClock`, `game.bidTimeouts` are DERIVED in `gameCodec.js`; no CODEC_V bump): a deadline is an instant on the old process and every restored human seat starts in reconnect grace, so a restored game gets a fresh clock (T0 = the restore kick) and no strikes. Since PR 5: (a) the restore kick (`persist/restoreGame.kick`, run when the restored table's gate opens; `restoreKit.kickRestored` is it) takes a restored BIDDING game through `gameHandlers.triggerBotIfNeeded(io, game, 'bid')` (its first line is `bidClock.onTurn`), so a human bidder gets that fresh clock; no clock runs while the gate is closed (`bidClock.eligible`); (b) the reversible holder self-fence (`GameState.suspend` / `unsuspend`) re-arms `'bidClock'` through `bidClock.afterSuspend` → `onTurn` (its same-turn resume, the deadline moved by the suspended time; a running clock is stopped and announced anew), never drops it (server/CLAUDE.md "Restored tables, the gate and the self-fence"). Tests: `bidClock.test.js` "live persistence", `persist/__tests__/gate.test.js`, `suspend.test.js"
- Codec versions: game `CODEC_V` 3 (2026-11-19) adds a log entry's optional `fault {position, bid, took}` (a hand's fault line; `SAVED.logEntry`); hydrate reads v1, v2 and v3 (`READ_VERSIONS`; v1 / v2 logs have no fault lines, nothing to convert; a rollback to code before v3 would discard v3 docs as `CodecError('version')`, as for every bump). `CODEC_V` 2 (2026-11-18, /help plan H2b) added `state.assist`, `game.assist` per position (`server/game/assistState.js`: the seat owner's username, counted /help uses, the `turnKey` of the last one, and the tutorial's reserved fields, all defaults until a later PR writes them). `hydrate` reads v1 and v2 (`READ_VERSIONS`): a v1 doc restores every seat with the default assist, so a game saved before the deploy survives it; `serialize` always writes the current version. A later bump keeps the older versions readable the same way (`gameCodec.v1Hydrate.test.js` hydrates real v1 docs from `__fixtures__/gameDoc.v1.json`)
- What is saved: a dealt game (BIDDING, PLAYING, TRICK_RESOLVING, HAND_RESOLVING; never the ambient demo or a pre-deal table) with its hands, bids, scores, seats (usernames), bots, the game log and its chat (players', spectators', bots'; the internal `from`), and for a lobby-born game its lobby (`lobbyOrigin`: the lobby name and every human member by username, the members who sat out and watched included; `casualVoice.lobbyExtras`; never its chat); a tournament from its creation (lobby included): name, members, host, scoreboard, rounds, chat (players' and spectators'), deadlines, the running score of each live table. A tainted or invalid game is not re-saved while it is so: its last good doc stays (hands and chat included) and later writes, a chat scrub's whole-log rewrite included, are skipped while that lasts (the next clean run clears the taint and the next change writes again; a pending whole-log rewrite stays pending until a write is acknowledged, so a skipped scrub still lands). Main-room and game-lobby chat are never saved; a tournament's lobby chat is (it is the tournament's chat). The spectator list is not saved (people re-spectate): a spectator's username is in a doc only on their chat lines and, for a lobby member, in `lobbyOrigin`
- Writes: game code never waits on one. Hooks (`GameState.nextSeq`, `_afterSeat`, `_applyTransition`, `addLogEntry`; `TournamentState._changed()` from every mutator, `broadcast` and the fields `tournamentHandlers` / `tournamentLiveness` write directly; a table's change marks its tournament too) mark the entity dirty; one `setImmediate` per entity serializes it after the synchronous run; one write in flight per entity, latest wins. First write `insertOne`; after its ack never an insert or upsert again: `updateOne({_id, owner: me, released: false})` with `$set` of the state and `$push {log: {$each: new lines, $slice: -500}}` (the whole log after a failed or ambiguous write, a chat scrub or an admin rename). `matchedCount 0` → `findOne`: gone at or past expireAt − 10 min → stop; anything else (gone early, another owner, mine but released) is a lost doc. Write mode never fences: nothing can adopt a 'write' doc, so a lost one was deleted or changed from outside (an operator, a restore, a rolled-back write); the store logs 'Live doc lost', stops saving that entity and play goes on. In 'on' a lost doc last written ownerMode 'on' (a casual table; with `createLiveStore({fenceOnLoss: true})` any doc) is a fence; a lost tournament or tournament-table doc ('write' until PR 6) is not (nothing adopts it: another instance's sweep discarded it after a false death of this one), so it stops saving and plays on, and its end still records stats and scores the round. A fence: the game is frozen and retired with no emit and no side effect, its sockets engine-closed (`socket.conn.close()`, never `socket.disconnect()`); a tournament is deleted from memory the same way. PR 5's sweep must never delete a doc whose owner instance is still alive, whatever its ownerMode
- Terminal claim and ENDED tombstone (`gameHandlers` gameEnd, `gameLifecycle.abortGame`; the one await in game code, at most 5 s, write mode never fences there; the claim and the stats write it holds up are ONE `trackInFlight` write, and the store's `close()` at SIGTERM ends every claim wait at once, so a slow claim never loses a game's stats to a shutdown): an ENDED game's doc becomes `kind: 'ended', ended: {record, score, seats, tournamentId, aborted}` (the gameRecords doc built once by `buildGameEndRecord`, the same object `recordGameStats(game, {record, onRecorded})` inserts) BEFORE the stats start; it is deleted only after the insert is acknowledged and, for a tournament table, after a tournament write listing it in completedGames. An aborted casual game's doc is deleted; an aborted tournament table becomes an `aborted` tombstone (record null). A tombstone left by a kill is what PR 5's adoption records exactly once (the unique gameId index); in write mode it expires by TTL. Nothing stays in memory for a game whose end did not go to plan: a claim that fails, or a record insert that fails for good (`recordSettled`, after `recordGameStats` settles), lets the game go and leaves its doc to the TTL (or the shutdown delete)
- Logs: never a doc, a hand or chat. Failures are warnings with the id and rev only (and the error name / code), at most one per kind per minute; the next change retries. A missing getter or null collection (tests that mock `../database` partially, before `connectDB`) skips silently
- Account deletion (write mode): `accountDelete.forgetAccount` drops the account's chat from every live game (by `from`) and tournament (by username) and the docs are rewritten whole; an admin rename / merge in the panel re-points `from` (`GameManager.renameChatSender`) and rewrites the log whole. Off, live chat in memory is left as before (hence the policy's Data Deletion wording, "from the saved state of any game or tournament still in progress": true in every mode)
- **Precondition for 'on' (PR 5)**: `gameRecords` must have its UNIQUE gameId index (`ensureGameIdIndex` may have fallen back to the non-unique `gameId_nonunique` on duplicates). `database.getGameIdIndexUnique()` (probed after `ensureIndexes`) shows as `/health` `persist.uniqueGameIdIndex`: check it is `true` before setting `write`; without it 'on' must run as 'write'
- **The database's own logs (plan ops 4.5, not a precondition):** the store's updates carry hands and chat (`$set` of the state, `$push` of the log lines), and mongod's default slow-operation log (`slowms` 100, sample rate 1.0) prints the whole update, filter and update document, of any operation slower than 100 ms (load, a failover, a 5 s server-selection stall), so MongoDB's own log may record a saved game update, chat included (checked on mongod 9.0.4). The owner chose (2026-11-17) not to change the MongoDB service and narrowed the privacy policy instead: text chat "is never written to our application's logs" (`server/routes/index.js`, Chat and Voice, pinned in `policyPages.test.js`). Our own logger still never writes a doc, a hand or chat (above). To stop mongod logging them anyway, start the Railway MongoDB with `--slowOpSampleRate 0` and check `db.runCommand({profile: -1})` shows `sampleRate: 0` after a restart (a per-database profile `filter` is not enough: the command-level line still prints the update)
- Backups: logical backups and restores exclude the three collections (`scripts/backup-db.js`, `scripts/restore-db.js`, from `dbBackup.LIVE_COLLECTIONS`; `database.test.js` checks it names exactly the collections `connectDB` opens); Railway volume backups (Layer 1) snapshot the whole volume, so they DO contain the live docs of their moment (within a day of their games; never adopted from: 'write' docs are never adoptable, and PR 5's age rule refuses old ones)
- **'on': adoption, resolve, liveness** (`server/game/persist/adopt.js`, through the store): liveness is judged on the observer's own monotonic clock, never by comparing clocks: an owner is dead once its instance doc's `(beatAt, beatSeq)` (or its absence) has been seen unchanged for 12 s; a beat older than 15 min is dead at once (coarse). The sweep runs at `start()`, then every 1 s for 3 minutes, then every 15 s; single flight, stopped at shutdown, never reads its own docs (`owner $ne me`). Another owner's doc is: pending (unreleased, owner not seen dead: never touched, whatever its mode); discarded (deleted by compare-and-set on owner and rev, then its players' `activeGameId` cleared, scoped): ownerMode 'write' (PR 5's tournament tables included; a tournament table saying 'on' is left for PR 6), an unreadable codec version, released more than 15 min ago or a dead owner's last beat more than 15 min ago (a same-deployment owner with an older startedAt, a crash restart, has no age limit), or a crash loop (an adopter dying within 60 s of `adoptedAt`, killed or crash-released, counts; the third quick death discards; the adopter's first write once the restore gate opens sets `adoptAttempts` 0); dropped if gameRecords already has the game; an ENDED tombstone: adopted, its record inserted once (`profileHandlers.recordEndedGame`: insertGameRecord's read-first and the unique index) and its stats applied once (the statsGames guard), pointers cleared, deleted (a record that fails keeps it, retried each sweep); a live doc: one `users.find` over its seat owners and chat senders (bot personas never): a missing, deleted or merged owner's seat becomes resignBot/gone with a fresh bot, a missing or deleted sender's chat is dropped (a merged one's stays), a name hold's `deletedAt` is learnt (`accountDelete.noteDeletedAccount`); then the compare-and-set `{_id, owner, rev}` → `{owner: me, released: false, adoptedBy, adoptedAt, adoptAttempts, rev + 1}`; then `restoreGame.adoptGame(io, doc, {now, abandonMs: 600000})` (the GAME side: hydrate, register, bots, the "This game resumed after a server update." line, the restore gate and the 10-minute restored abandon) and the store writes it on as updates. One op per id at a time (sweep and resolve share it). `store.resolve(gameId)` → `{state: 'memory'|'adopted', game}`, `{state: 'pending'}` (another live instance holds it; an id nobody lists while an older live 'on' instance exists; any id while this process shuts down) or `{state: 'gone'}`, after waiting (3 s at most) for connectDB and the boot sweep; `store.whenAdopted(gameId, ms)` resolves with the game once adopted (for a parked socket). A claimed doc that fails to hydrate is deleted (a failed delete is retried each sweep), and `resolve()` removes an own live doc the store does not hold (no adoption settling, no terminal claim pending) and answers 'gone', so no pointer stays 'pending' for good. Holder self-fence: 8 s on this process's clock without an acknowledged heartbeat suspends every casual table with a doc (`game.suspend()`, not saved meanwhile), checked every second AND synchronously before any game timer, lifecycle pause or bot action runs (`persist/hooks.beforeRun`: a process thawing from a freeze runs its overdue timers before the interval; a run whose game it just suspended is held for the thaw); the next good beat re-takes each doc with a compare-and-set write (`findOneAndUpdate {_id, owner: me, released: false, kind: 'live'}` → `rev + 1`, which also makes an adopter's claim still in flight on the old rev fail): matched → `game.unsuspend(io)`, anything else → fenced (frozen, retired with no emit, sockets engine-closed). The room is told (owner 2026-11-19, "Pause with a notice"; the L7 outage froze tables ~25 s with no message): players, lazy watchers and spectators get the system line "Game paused: the server is reconnecting. It will resume on its own." once when the table is suspended (not again while it stays suspended, a failed re-take included) and "Game resumed." once after a matched re-take unsuspends it; a fenced table gets no resume line (its sockets close, the players reconnect to the adopter). Each is `game.unsavedNotice(io, line)` (`liveStore` PAUSE_NOTICE / RESUME_NOTICE), the same mechanism as the shutdown notice to a frozen table (`noticeGames`): a `gameLogEntry {message, type: 'system', seq}` room emit that bypasses the suspended emit gate, NOT added to gameLog (so in no snapshot's log, no saved doc, no logTotal), no persist hook, no RNG. Its seq is `++eventSeq`, the next one (R1): every client gate (web, iOS source, shipped iOS <= 18) applies it as the next event, and a snapshot during or after the pause carries the bumped seq, so the next broadcast is S + 1 with no gap or repeat (reusing the seq instead would get the line, or the next real event, dropped as a duplicate, R2). The only saved trace is that `eventSeq` counter, written with the game's next save after the thaw (a restore adds 1000 to it anyway). Write mode never self-fences, so it sends neither line (off and write are unchanged on the wire). After the store closes (handoff, crash release) a late write that finds its doc released fences nothing. A fenced game's terminal claim answers 'fenced', so its gameEnd records no stats, clears no pointer and scores nothing. A late heartbeat never moves `beatSeq` back (its filter). ## Startup DB and indexes

- Startup DB (`server/database.js`): `connectDB` runs fire-and-forget after `listen()`, retries the connect with backoff (2 s doubling, max 30 s; each attempt gives up after the 5 s server selection timeout below), assigns the collections and resolves `whenReady()`, then `ensureIndexes()` (`Promise.allSettled` of `safeIndex` per index: `gameRecords.completedAt_-1`, unique `gameRecords.gameId_1` via `ensureGameIdIndex` (partial `{gameId: {$exists: true}}`, which an equality lookup still uses; a `$type` filter would not be), `gameRecords.statsPending_partial` (the startup sweep), `reports.createdAt_-1`, unique `users.username_1` via `ensureUsernameIndex`; both unique builds go through `ensureUniqueWithFallback`); each failure is a warning and startup continues (existing duplicates → no unique index, but a non-unique `username_nonunique` / `gameId_nonunique` fallback so lookups stay indexed; a later boot drops the fallback and retries the unique build). Only `createIndex` (MongoDB 4.0+); no backfills. `signIn`/`restoreSession`/`signUp` and the `rejoinGame` token check wait up to 10 s on `whenReady` when the collection is still undefined (a failed restore makes both clients forget their token). `server/__tests__/realMongo.test.js` checks indexes/plans/race/payload equality against a localhost mongod (scratch DB, skips green without one unless `REQUIRE_REAL_MONGO=1`, as in CI, which fails it instead; never call `connectDB` from tests: its dbName is `DB_NAME`, else `babonline`, `server/config/dbName.js`; a MONGO_URI path is never the data database, `server/admin/CLAUDE.md` Account Admin)
- Mongo outages after startup: the client is made with `serverSelectionTimeoutMS: 5000` (`SERVER_SELECTION_TIMEOUT_MS`; the driver default is 30 s), so with no reachable server every operation rejects after ~5 s. Every in-game DB await swallows that error and play continues: the draw screen's picture lookups (`getUserProfilePic`) and `setActiveGame` before `teamsAnnounced` (~5 s each), `recordGameStats` (background, retried: End-of-game writes below), `clearActiveGameForAll` before tournament scoring (~5 s). `server/socket/__tests__/dbOutage.test.js` plays a whole tournament with every DB call rejecting after 5 s
- `users.username` has a unique index, created at startup (`ensureUsernameIndex`); if existing duplicates block it the server logs a warning and runs with the non-unique `username_nonunique` fallback until they are merged. `signUp` treats a duplicate-key error as "That name is taken." Active-game DB writes (`setActiveGame`, `clearActiveGameForAll`) go to each seat's `ownerUsername` (none for native bots; `setActiveGame` also skips resigned and gone seats); `clearActiveGameForAll` only clears users whose `activeGameId` is still that game (a leaver may be in another game by then). Both run as one `Promise.all` of the per-user helpers (deliberately not `updateMany`: same latency at 4 users, per-user error isolation, the tests' `updateOne` spies), still awaited: game start writes before `teamsAnnounced` (sign-in auto-rejoin reads it) and re-clears every launched write if aborted meanwhile (and a seat's write if it was resigned or /leave'd during the batch); the end path clears before tournament scoring. Stale-pointer clears on signIn/restoreSession/rejoinFailed are scoped to the stale id (`clearActiveGame(u, staleId)`), so a pointer a new game wrote meanwhile survives
- End-of-game writes (2026-11-15; `profileHandlers.recordGameStats`, still started in the background after `gameEnd`): (1) the `gameRecords` entry goes in first with `statsDeltas {bucket: 'stats'|'botStats', byPosition: {<pos>: the 12 counters}}` (no names) and `statsPending [{position, username}]` (the human owners still to credit; a player deleted mid-game is left out); each attempt first looks the gameId up and E11000 on the unique index means another writer won, so the stored entry (and its pending list, none once applied) is used; (2) each pending player's `$inc` is guarded in the same update: filter `statsGames.id: {$ne: gameId}` and `mergedInto: {$exists: false}` (a tombstone is never credited), `$push` of `{id, at}` into `users.statsGames` (the last `STATS_GAMES_KEPT`, 50; server-only, never on the wire, left out of the sign-in projection, unset on a merge tombstone), so applying it twice counts once; for a record read back (a replay, the sweep) the filter also needs the list to have room or its oldest `at` to be older than the game's `completedAt` less `STATS_GUARD_SKEW_MS` (10 min, clock skew between processes), since a full newer window may have dropped the id: such a game is not credited (warned with the delta) rather than risk counting it twice; (3) `statsPending` is `$unset` (or cut to the players whose write failed for good), so the usernames leave the record. Every step retries any failure after 1, 2, 4, 8, 16 s (every step is idempotent); once a graceful shutdown starts, a pending wait ends at once and later ones are 250 ms at most, and a step keeps retrying until the drain's deadline even past its 5 retries, so a short outage during a deploy (a failover) still lands the game; a record that cannot be written at all is logged with its deltas and the stats still go in once. One chain per game per process (a second call joins it); `trackInFlight` makes a graceful shutdown wait for it. `resumePendingGameStats` (server/index.js, once after `connectDB`) finishes every record still carrying `statsPending` (a crash, an outage longer than the retries), safe while another process applies the same record. Accepted: a pending record keeps the pending usernames until it is applied or swept (seconds normally; an account deletion pulls its own entry, `eraseAccount`, and the sweep clears an emptied list); a rename or merge of a player in that window credits nobody (the old name is a tombstone, which the filter skips; the new name is not followed, since a merge target's guard does not hold the source's ids), and a record swept after its players' windows moved past it is not credited: both warn 'Game stats not credited: …' with the delta for a manual fix. Records from before 2026-11-15 have no `statsDeltas`. Per-seat bucket (2026-11-18, /help plan H2a, reader only): `applyPendingStats` credits each seat to `statsDeltas.bucketByPosition[<pos>]` when that names a bucket (`'stats'` or `'botStats'`), else to the whole-game `bucket` as before (`seatBucket`; an unknown value, or a `bucketByPosition` that is not a plain object, falls back to the whole-game bucket, so a value never becomes a field path); the same per-seat bucket goes into the 'Game stats recorded' info line, the 'Error recording game stats' error and every 'Game stats not credited' warning. The writer (2026-11-18, /help plan H2c, `buildGameEndRecord`) adds it only for a seat whose owner made more than 3 counted /help uses (`assistState.isAssistedSeat`): `{<pos>: 'botStats'}` when the whole-game bucket is 'stats' (in a bot game anyway it adds none), plus `withBots: true` on the record (empty `teamNBots` for human seats: the game's team records move to the "with bots" Records scope, all four players' records, by the owner's Q4) and the server-only `assistedTeams: [1|2]` (no Records projection carries it); every seat with counted uses goes in `statsDeltas.assist {<pos>: {help}}` (by position, never by name). This writer ships after the reader (H2a) has been deployed, so no running process (including an older one adopting an ENDED tombstone, which carries the prebuilt record) meets a record it would credit to the wrong bucket. A game nobody used /help in gives exactly the record it gave before (`assistRecords.test.js` holds it byte for byte); records without these keys route as before (`docs/claude/assist.md`, /help on the server). Tests: `server/socket/__tests__/gameStatsWrites.test.js` (memoryDb with failing writes and lost replies, the sweep, shutdown, per-seat buckets), realMongo (p)

## Backups and restore

Why: there are no transactions, and `users.stats` / `users.botStats` are cumulative `$inc` counters that cannot be rebuilt from `gameRecords` (records before 2026-11-15 carry scores and names, not per-player tricks, sets, faults or HSI (since then `statsDeltas` holds each seat's counters, by position, not by name), and bot games before 2026-11-13 have no records at all). A merge is partly reversible: the kept account's `mergedFrom[]` entries hold each source's `stats` and `botStats` at merge time (the tombstone has no password or sessions left, so an un-merge also needs a new password). A delete (the player's own or the admin panel's: user document gone, records anonymized to `[deleted]`), a buggy stats change, a bad manual edit or a lost volume is permanent without a backup. Two independent layers, both the owner's to run:

### Layer 1: Railway volume backups (dashboard only)

- Turn on: project canvas → MongoDB service → **Backups** tab. Schedules (pick any, several at once): daily (kept 6 days), weekly (kept 27 days), monthly (kept 89 days); **Backup now** makes a manual one, capped at 50% of the volume (5 GB volume, ~635 MB used: fine). Incremental, copy-on-write, billed like volume storage for the data unique to the backups. Railway calls the feature "still under development"; whether the Hobby plan has it is not stated in its docs (checked 2026-11-15): the tab shows it or not
- Restore: Backups tab → the dated backup → **Restore**. Railway makes a NEW volume from it, mounted at the same path; the current volume stays in the project, unmounted (so writes after that backup are still on it until you delete it). The change is staged: **Details** / **Deploy** on the canvas applies it and redeploys the MongoDB service. Downtime is that redeploy (seconds to minutes); the app keeps running meanwhile, every DB call fails after ~5 s and games go on (`dbOutage.test.js`), stats of games that end in the gap are lost, and it reconnects by itself. Everything written after the backup is lost (left on the old volume)
- Contents: the whole volume, so also the live-game documents of that moment (`liveGames`, `liveTournaments`, `serverInstances`: seats, hands, game logs and game / tournament chat; Live game persistence). Unlike layer 2 they cannot be left out; they go when the backup expires (the policy's Backups line, "within 3 months"). In a restored volume they are stale: their TTL (`expireAt`, a day after the game was created) lets mongod's TTL monitor delete them within about a minute when that day has passed, and an 'on' instance (deploy survival PR 5) never adopts them (the adoption age rule, 15 min)
- Limits: "wiping a volume deletes all of its backups", restores go only into the same project and environment, and the retention is at most 89 days. Nothing here survives losing the volume, the project or the account, or a mistake found later: hence layer 2

### Layer 2: logical backup, `scripts/backup-db.js` (owner-run on your machine)

- Needs: macOS or Linux (the URI reaches the tools through `/dev/fd`), a checkout with `npm ci` (Node 24) and the MongoDB Database Tools (`brew install mongodb-database-tools`: mongodump / mongorestore / mongoexport / mongoimport 100.x; the drill used 100.16.1). mongosh is not needed
- A URI that works from your machine: the app's `MONGO_URI` is the private-network one (`MONGO_URL`, a `*.railway.internal` host), unreachable from outside. Railway databases are private by default: MongoDB service → **Settings → Networking → Public Access** adds a TCP proxy and the variable `MONGO_PUBLIC_URL`. Egress through it is billed (about one archive per backup). It exposes mongod to the internet behind the root password Railway generated: leave it on, or turn it on for a backup and off after (the proxy host/port can change; `MONGO_PUBLIC_URL` follows). Owner's call
- Run it from the linked checkout, with the URI never on screen, in a command line or in shell history (single quotes: the inner shell expands it, not yours):
  ```bash
  railway run --service MongoDB -- sh -c 'MONGO_URI="$MONGO_PUBLIC_URL" node scripts/backup-db.js --out ~/bab-backups --keep 12'
  ```
  `railway run` injects that service's variables into that one command only (use the service's name as the canvas shows it; the flags are from `railway run --help`, CLI 5.71; never tried against the project). Never `export MONGO_URI=<production>` in your shell: `merge-accounts`, `set-password`, `set-admin` and a local `npm start` all read `MONGO_URI` and would then act on production. The script reads `MONGO_URI` from the environment only (never `.env`, no default)
- What it does: refuses `--out` inside this repository or any git work tree (symlinks resolved; `.gitignore` also ignores `*.archive.gz`); hands the URI to mongodump through a pipe (`--config=/dev/fd/3`), so it is never in `ps` or in a file (a run killed or cut off by closing the terminal leaves no password behind; Ctrl-C, `kill` and SIGHUP also stop mongodump and remove the `.partial`); makes the auth database explicit (`authSource`: the URI path, else `admin`), because `mongodump --db babonline` otherwise logs in against `babonline` and Railway's root user lives in `admin` ("Authentication failed", found in the drill); writes `<dir>/babonline-<UTC>.archive.gz.partial`, refuses a dump whose `users` is missing or empty (the accounts are gone or it is the wrong database: such a dump must not pass for a backup or push good ones out with `--keep`; `--allow-no-users` overrides, never together with `--keep`), reads the whole gzip stream back, saves it under its final name without ever replacing an existing archive (names have one-second resolution: a second run in the same second is refused) and sets 0600; prints per-collection counts, size, time and SHA-256, never a document; never dumps the live-game collections (`--excludeCollection` for each of `dbBackup.LIVE_COLLECTIONS`: `liveGames`, `liveTournaments`, `serverInstances`; games in progress are kept at most a day, privacy policy "Games in progress"), and says so on its `Skipped:` line; `--keep N` then deletes all but the newest N `babonline-<UTC>.archive.gz` in that folder (nothing else). Any URI in a tool error is printed as `mongodb://***@host`. Exit 0 ok, 1 failed (nothing kept), 2 usage (nothing kept), 3 archive kept but pruning failed. `--db` (both scripts) defaults to DB_NAME from this shell, never `.env` (like MONGO_URI), else `babonline`; the `Source:` / `From:` line names the source, and a bad DB_NAME is exit 2
- Not point in time: on a standalone mongod (no oplog) mongodump copies collections one after another while the server writes, so a game ending mid-dump can have its record without its stats or the reverse. Run it at a quiet hour
- How often: weekly, and always right before anything risky (a merge batch, deploying a stats or schema change, a hand edit in the DB, a restore). Layer 1 covers the days between
- Where to keep archives: they hold every bcrypt password hash, every session-token hash, any legacy plaintext `sessionToken` (accounts that have not signed in since per-device sessions; the server still accepts one, so an archive can hold live sign-ins in the clear), reports and the admin audit. On an encrypted disk (FileVault, an encrypted external drive) plus one copy off the machine: an attachment in your password manager, or an `age`/`gpg`-encrypted file in private cloud storage. Never the repository, never a shared or public folder, chat, issue or email. Check the SHA-256 after copying. Prune (`--keep`): deleted accounts live on in old archives until they go (see the privacy note below)

### Restoring

Always first: back up the CURRENT state, broken or not (it keeps the writes since the good archive, and undoes the restore if it was the wrong call). Restore production (a layer-1 volume or a layer-2 archive) only with `LIVE_PERSIST=off` or with no live games (`/health` live.games 0): the running server's live documents are not in the restored data, so the store finds its documents gone and stops saving those games and tournaments (write mode: they play on unsaved; with PR 5's 'on' a vanished document is a takeover and that table ends). Then:

- **Inspect in a scratch database** (always the first step; needs a local mongod: `brew tap mongodb/brew && brew install mongodb-community`, then `mongod --port 27999 --dbpath ~/bab-restore-db` in its own terminal after `mkdir ~/bab-restore-db`):
  ```bash
  node scripts/restore-db.js ~/bab-backups/babonline-<UTC>.archive.gz --uri mongodb://127.0.0.1:27999 --into-db babonline_restore_20261115
  ```
  `--into-db` (or `--nsFrom 'babonline.*' --nsTo '<name>.*'`) restores under another name. It refuses a non-empty target unless `--drop` (drops each archived collection first), builds any missing index with `server/database.js` `ensureIndexes`, never restores the live-game collections, in either mode, even from an archive that has them (one made by an older checkout: `--nsExclude=<db>.<collection>`, the archive's name, which mongorestore matches before `--nsFrom` / `--nsTo` rename it; `--drop` drops only what it restores, so the target's own live documents stay as they are), and prints counts, index names, users / merged names / saved sessions / players with stats, the newest game's time, and a sanity check (`users` is not empty, every user has a username, every account a bcrypt hash, the unique `users.username_1` could be built, i.e. no duplicate names; exit 1 otherwise). Look at documents with mongosh or Compass. The target is `--uri` (no credentials allowed there: shell history) or `RESTORE_URI`; `MONGO_URI` is never used, so a leftover export cannot aim a restore at production
- **Put back specific documents** (e.g. a wrongly deleted user), from the scratch copy, in insert mode (it never overwrites: an existing `_id` or a name taken since by a new sign-up is refused, `1 document(s) failed`):
  ```bash
  umask 077
  mongoexport --uri mongodb://127.0.0.1:27999 --db babonline_restore_20261115 --collection users --query '{"username":"Alan"}' --jsonFormat=canonical --out alan.json
  railway run --service MongoDB -- sh -c 'mongoimport --uri "$MONGO_PUBLIC_URL" --authenticationDatabase admin --db babonline --collection users --mode insert --file alan.json'
  rm alan.json
  ```
  Then **redeploy or restart the bab-online service** (canvas → bab-online → its deployment's menu → Restart or Redeploy) before telling the player: a deletion puts the name in the server's in-memory `deletedUsernames`, so until a restart every game the restored player finishes is recorded as `[deleted]` (and the leaderboard / records caches and avatar store still treat the account as gone). Games they play between the import and the restart stay `[deleted]`.
  `--authenticationDatabase admin` is required (as above), and these raw tools print the WHOLE URI, password included, on a connection error: do not paste their output anywhere. `--jsonFormat=canonical` keeps types (dates, int vs double). The restored account signs in with its old password, and its devices' saved sessions from the archive work again; its past games stay `[deleted]` and other players' block lists stay as they are now (fixing those is a one-off script: ask). For stats drift, never put an old user document back over a live one (it erases every game since): work out the per-player difference from the scratch copy and `$inc` it, with a dry run first
- **Full restore into production** (last resort: lost volume or mass damage, and no usable layer-1 backup):
  1. Back up the current state (if any) and check the archive in a scratch database (above)
  2. Stop the app's writes: bab-online service → its active deployment's menu → Remove (players see the site down; check the dashboard's wording)
  3. `railway run --service MongoDB -- sh -c 'RESTORE_URI="$MONGO_PUBLIC_URL" node scripts/restore-db.js ~/bab-backups/babonline-<UTC>.archive.gz --i-mean-production --drop'`: it shows the target host (`<-- NOT LOCAL`) and restores only after you type `babonline`. Without `--i-mean-production` any host but localhost / 127.0.0.1 / ::1 is refused (an SSH tunnel on a local port counts as local: never tunnel production to a port you restore into)
  4. Redeploy bab-online, check `/health` (`db: connected`) and sign in
  - What it loses: everything since the dump. Accounts created since (their names are free again; those players sign up again), games, stats and records, reports, admin-audit entries, reset links. Undone: password changes (an old password works again) and session revocations (redo any Sign out everywhere / reset since the dump), merges and renames. Back: accounts deleted since, including players' own deletions; delete them again (diff the usernames of the pre-restore backup against the restored database). Sessions: `users.sessionTokens` is in the dump, so every device signed in at dump time stays signed in (drilled: a pre-dump token restores after the restore); a device that signed in later signs in again
- Privacy note for the owner: `/privacy` says deletion removes data "immediately"; copies in backups remain until rotated (layer 1: up to 89 days; layer 2: your `--keep`). Adding a line such as "Copies in encrypted backups are deleted within 90 days." is the owner's decision. The App Store privacy labels describe data collected and its use, not backups, so they should not change

### Proposal: scheduled backups (not built; owner decides)

A Railway cron service in the same project (schedule `0 9 * * *`, UTC; it must exit after each run) that runs `mongodump --uri "$MONGO_URL" --authenticationDatabase admin --db babonline --gzip --archive` over the private network (no public proxy needed), pipes it through `age` with a public key only (the service can encrypt but never read; the private key stays in your password manager) and uploads the result to a Railway Bucket (S3-compatible) with a lifecycle of ~30 days. Cost at today's size: storage $0.015 per GB-month (≈ 12 GB kept ≈ $0.20/month), the upload counts as egress since buckets are not on the private network (≈ 12 GB/month), plus a few seconds of compute a day: well under $2/month. Steps: create the bucket; add a service from a small image with the Database Tools, `age` and an S3 client; set its variables by reference (`${{MongoDB.MONGO_URL}}`, the bucket's credentials, the age public key); set the cron schedule; check one run's object restores here (`age -d` then restore-db.js). Trade-off: a bucket in the same Railway account does not survive losing the account; an outside bucket (Cloudflare R2, Backblaze B2) does, at similar cost. Until then, the weekly owner-run backup above is the off-Railway copy

- Stats scopes (owner 2026-11-13: "you can choose to see standings including human and bot games, human only, or human plus bot only ... default to human only"; `server/utils/statsScope.js`): `users.stats` stays the HUMAN-games bucket exactly as before (same fields and rules; every shipped iOS build and every existing reader sees it); a game with any `bot` or `resignBot` seat at the end (solo games, tournament tables with filler bots, a resigned seat) `$inc`s the parallel `users.botStats` (same 12 fields) for every seat with a human owner (the `getOriginalPlayer` + `ownerUsername` rule: lazy, resigned and /leave'd owners included) and inserts its `gameRecords` entry with `withBots: true`, `team1Players`/`team2Players` holding ONLY the human owners (seat order, `recordName`) and `team1Bots`/`team2Bots` the persona names of the seats without an owner ('🤖 Mary'; a team of two bots has `teamNPlayers: []`). Nothing from before 2026-11-13 exists for bot games (no backfill). Readers: `getProfile` / `getLeaderboard` / `getRecords` / `getPlayerProfile` take an optional `{scope: 'human'|'bots'|'all'}` (`normalizeScope`: missing, non-object or unknown = `human`, never refused; `getPlayerProfile`'s Joi key is `Joi.any()` so `stripUnknown` keeps it and a non-string, null or long scope is normalized, not refused; `socket/index.js` forwards the payload of the three safeHandler events; their c2s contract payload stays the open property-less one, documented by examples and notes, since a payload WITH properties needs a Joi schema and their `joi: null` is frozen by the baseline). `human` = today's reply byte for byte (`profile.stats` is the RAW stored bucket, a legacy 6-key document stays 6 keys; records filter `withBots: {$ne: true}`, same projection, still three finds, the thisMonth/thisYear finds still on `completedAt_-1`); `bots` = `botStats` / `withBots: true` records; `all` = `stats + botStats` summed field by field (`sumBuckets`) / every record. The leaderboard reads every player with `gamesPlayed > 0` IN THAT SCOPE (all: either bucket) and the Population row averages all of them, but only a player with `LEADERBOARD_MIN_GAMES` (5) or more games in that scope gets a row of their own (owner 2026-11-14: hide, don't list unranked, so every shipped client is right with no app change; profiles, records and search ignore it; the web says "Players appear in the standings after 5 games." under the table; `leaderboardMinGames.test.js`, and the older leaderboard suites pin the minimum to 1 with `_setLeaderboardMinGamesForTests`). Records in bots / all: `players` = the humans then the bot personas (strings, the wire type is unchanged), and a team of two bots never holds the highest/lowest score or most/least bags (biggest win always has a human side). Echo rule: the reply carries a top-level `scope` ONLY when the request had a `scope` key (so iOS and every payload-less caller get exactly the old bytes; the web always sends one and drops a reply for another scope). leaderboardResponse / recordsResponse failures echo it too (iOS 1.2.1 build 8 files a failure under the scope that asked; the web drops a stale one); profile failures do not. `searchPlayers` rows stay human games (a lookup, not standings). ## Soft limits

- Soft limits (`rateLimiter.limits`, per socket): `getLeaderboard`/`getRecords` 10/10 s are checked inside their handlers and over the limit reply with the cached (even stale) page OF THE REQUESTED SCOPE, its fill in flight, else the ordinary `{success:false, message}` — never `serverError` (one budget for every scope: fast switching counts against it; the web control coalesces quick switches, 200 ms); `searchPlayers`/`getPlayerProfile` 30/10 s through `asyncHandler` (`serverError {code:'rateLimit'}`, a web toast; Joi since V1_REMOVALS #18, as for `joinLobby` (a uuid) and `removeBot` (a `bot:` id; `removeBotFromLobby` also refuses a human member); both web-only). Session and table entry (2026-11-15, generous: every reconnect is a new socket): `restoreSession`/`rejoinGame` 10/min, `joinLobby`/`joinAsSpectator` 20/30 s, `updateProfilePic` 30/min through the wrappers, `getProfile` 20/10 s checked in `profileHandlers.getProfile` (no schema); the no-payload `joinMainRoom` 30/min, `playerReady`/`playerUnready` 20/10 s, `leaveLobby`/`addBot` 20/30 s through `safeHandler(fn, { limit })` (checked at the socket event only, never on internal calls such as joinMainRoom leaving a lobby); all answer `serverError {code:'rateLimit'}` over the limit (a refused restoreSession never gets a `restoreSessionResponse` failure, which makes iOS forget its token). `rateLimiter.unlimited` lists the wrapped keys left unlimited on purpose (`forceResign`, `removeBot`); any other key with no limit warns once per key outside production (`eventLimits.test.js` checks every `socket.on` in index.js: a wrapper key with a limit, a `safeHandler` limit, one of the events checked inside their handlers (clientHello, getProfile, getLeaderboard, getRecords, the voice signals), or `unlimited`). - Block list (`server/socket/safetyHandlers.js`): `blockUser` needs a target that is an account (a tombstone counts) or a `🤖 ` bot name (bots chat, and iOS 1.2.0 offers Block on any chat line), else `blockListUpdated {success:false, message: 'No player by that name.'}`; the list holds at most `BLOCK_LIST_MAX` 200 names (the write is guarded on `blockedUsers.199` not existing; full: 'Your block list is full (200 players).
