# Server: database, caches, limits, HTTP pages and avatars

Never auto-loaded: open it for `server/database.js`, DB reads/writes, profile caches, soft rate limits, the Express pages, the avatar pipeline, CI (`.github/workflows/ci.yml`), deploys (`.railway/railway.ts`, `/health`, `/ready`, crash exits, `LOG_LEVEL`), or backups and restores (`scripts/backup-db.js`, `scripts/restore-db.js`, Railway volume backups).

## Deploys, crashes and health

- Service settings are infrastructure as code: `.railway/railway.ts` (Railway's IaC, `railway/iac`; `railway.toml` config as code is deprecated and stops being read on 2026-12-01; removed here 2026-11-15). It is NOT applied on push: from a checkout linked to the project (`railway status` shows project beautiful-analysis, environment production) run `npm install --no-save railway@3.17.0` (the SDK the file imports; kept out of package.json so CI and production never install it), then `railway config plan` and, if the diff is what you meant, `railway config apply`. Variables are unmanaged (`variables: { managed: false }`): MONGO_URI, the TURN keys and PORT live only in the dashboard, never in this public repository. What it sets on the `bab-online` service:
  - `source.checkSuites: true` (Railway's "wait for CI"): a main commit deploys only after its GitHub checks pass, so a red CI never ships (before 2026-11-15 every push deployed regardless). A main commit whose CI fails needs a fix commit or a manual redeploy
  - builder NIXPACKS (Node from package.json `engines`, 24.x); Railpack, the default for new services, would be a separate move
  - deploy healthcheck `/ready`, timeout 120 s: a new deploy takes traffic only once `/ready` answers 200 (DB ping); one whose DB never connects within the timeout fails and is never switched to, so the old deploy keeps serving. 120 s covers connectDB's backoff on a slow Mongo (each attempt gives up after 5 s). Railway probes `$PORT`, from `healthcheck.railway.app`; the service variable `PORT=3000` (set 2026-11-15) matches the hard-coded `server.listen(3000)` and the domain's target port (babonline.io → 3000). Without it Railway injects 8080 and the probe fails every deploy: a `/health` healthcheck (53509f3) was pulled 25 minutes later in a646178 for that reason. index.js logs `PORT is N but the server listens on 3000` at boot if they ever differ again. First healthcheck-gated deploy: 2026-11-15, "[1/1] Healthcheck succeeded!"
  - restart policy: Railway's default, ON_FAILURE with 10 retries, so a crash (exit 1) is restarted and a deploy's SIGTERM (exit 0) is not. Not written in the file: Railway stores the default as null, and an explicit value shows as a change in every plan
  - domain babonline.io → port 3000, one replica in us-west2
- Crash exits (`server/utils/shutdown.js`): SIGTERM/SIGINT exit 0 (a deploy's stop: no restart), `uncaughtException` exits 1 (Railway restarts it ON_FAILURE; before 2026-11-15 a crash exited 0 and the site stayed down until the next deploy). Both run the same graceful path: `server.close`, `serverShutdown {message}` to every socket, 1 s, `io.close`, the end-of-game writes still in flight (`trackInFlight`, at most `HARD_EXIT_MS` minus the fixed waits and a 1 s margin, 7.5 s; their retry backoffs are cut short, `retryDelay`; logs 'Exiting with writes still in flight' if any are left), 0.5 s, exit; a hard deadline (`HARD_EXIT_MS`, 10 s) exits with the same code if anything wedges, and a throw inside the shutdown still exits. A second reason while one is running forces the exit at once with the FIRST reason's code (a crash during a deploy's SIGTERM exits 0). `unhandledRejection` is logged only. Tests: `server/__tests__/shutdownExitCodes.test.js` (exit stubbed), `serverShutdown.test.js` (real Socket.IO)
- Timer callbacks never crash the server: a throw in a bare `setTimeout`/`setInterval` callback is an uncaughtException, i.e. a restart that drops every game. Server timers use `server/utils/safeTimer.js` (`safeTimeout(fn, ms, label)` / `safeInterval`: same timing and handle, a sync throw or async rejection is `logger.error('Timer callback failed', {timer, error, stack})`): bot chat, lobby-seat grace, completed-tournament cleanup, other-closed notice, the delete-account disconnect, the rate limiter's sweep, the upgrade gate's pushes; game timers use `game.setTimer` (guarded the same way) and bot bid/play/draw have their own try/catch. `safeTimer.test.js` scans `server/` and fails on any new bare timer not in its list
- `GET /health` (`server/routes/health.js`): always 200 and cheap (no DB round trip), for liveness and for a look before pushing: `{status:'ok', timestamp, uptime, memory, db, live}`; `db` is 'connected' | 'disconnected' from the driver's own topology events (`database.getDbState`: connected and a writable server seen; transitions logged as "MongoDB unreachable" / "MongoDB reachable again"); `live` = `{sockets, games, tournaments, lobbies}`: connected Socket.IO sockets, live games with at least one human seat owner or human entrant (`GameManager.getHealthCounts`; the ambient demo and other bot-only tables left out), tournaments not complete, open lobbies; a count that cannot be read is null. Counts only, never a username or id (the endpoint is public). `GET /ready` pings the DB (503 without it) and is the path for a deploy healthcheck once one can be set (above); `/live` is a bare 200. Tests: `server/__tests__/healthRoute.test.js`
- `LOG_LEVEL` (`server/utils/logger.js` `resolveLevel`): error | warn | info | http | debug (any case) sets the level; unset, blank or unknown (reported once on the console) keeps the default, debug in development and info elsewhere. The log format is unchanged. Log files (`logs/combined.log`, `error.log`) are written only on local runs (`fileLogsEnabled`: off under test, `NODE_ENV=production` or any `RAILWAY_*` environment id), so Railway's stdout logs are the only server logs, as the privacy policy says. Chat text and a report's reason never go into a log line (`reportLogLine.test.js`)

## Startup DB and indexes

- Startup DB (`server/database.js`): `connectDB` runs fire-and-forget after `listen()`, retries the connect with backoff (2 s doubling, max 30 s; each attempt gives up after the 5 s server selection timeout below), assigns the collections and resolves `whenReady()`, then `ensureIndexes()` (`Promise.allSettled` of `safeIndex` per index: `gameRecords.completedAt_-1`, unique `gameRecords.gameId_1` via `ensureGameIdIndex` (partial `{gameId: {$exists: true}}`, which an equality lookup still uses; a `$type` filter would not be), `gameRecords.statsPending_partial` (the startup sweep), `reports.createdAt_-1`, unique `users.username_1` via `ensureUsernameIndex`; both unique builds go through `ensureUniqueWithFallback`); each failure is a warning and startup continues (existing duplicates → no unique index, but a non-unique `username_nonunique` / `gameId_nonunique` fallback so lookups stay indexed; a later boot drops the fallback and retries the unique build). Only `createIndex` (MongoDB 4.0+); no backfills. `signIn`/`restoreSession`/`signUp` and the `rejoinGame` token check wait up to 10 s on `whenReady` when the collection is still undefined (a failed restore makes both clients forget their token). `server/__tests__/realMongo.test.js` checks indexes/plans/race/payload equality against a localhost mongod (scratch DB, skips green without one unless `REQUIRE_REAL_MONGO=1`, as in CI, which fails it instead; never call `connectDB` from tests: its dbName is `babonline`)
- Mongo outages after startup: the client is made with `serverSelectionTimeoutMS: 5000` (`SERVER_SELECTION_TIMEOUT_MS`; the driver default is 30 s), so with no reachable server every operation rejects after ~5 s. Every in-game DB await swallows that error and play continues: the draw screen's picture lookups (`getUserProfilePic`) and `setActiveGame` before `teamsAnnounced` (~5 s each), `recordGameStats` (background, retried: End-of-game writes below), `clearActiveGameForAll` before tournament scoring (~5 s). `server/socket/__tests__/dbOutage.test.js` plays a whole tournament with every DB call rejecting after 5 s
- `users.username` has a unique index, created at startup (`ensureUsernameIndex`); if existing duplicates block it the server logs a warning and runs with the non-unique `username_nonunique` fallback until they are merged. `signUp` treats a duplicate-key error as "That name is taken." Active-game DB writes (`setActiveGame`, `clearActiveGameForAll`) go to each seat's `ownerUsername` (none for native bots; `setActiveGame` also skips resigned and gone seats); `clearActiveGameForAll` only clears users whose `activeGameId` is still that game (a leaver may be in another game by then). Both run as one `Promise.all` of the per-user helpers (deliberately not `updateMany`: same latency at 4 users, per-user error isolation, the tests' `updateOne` spies), still awaited: game start writes before `teamsAnnounced` (sign-in auto-rejoin reads it) and re-clears every launched write if aborted meanwhile (and a seat's write if it was resigned or /leave'd during the batch); the end path clears before tournament scoring. Stale-pointer clears on signIn/restoreSession/rejoinFailed are scoped to the stale id (`clearActiveGame(u, staleId)`), so a pointer a new game wrote meanwhile survives
- End-of-game writes (2026-11-15; `profileHandlers.recordGameStats`, still started in the background after `gameEnd`): (1) the `gameRecords` entry goes in first with `statsDeltas {bucket: 'stats'|'botStats', byPosition: {<pos>: the 12 counters}}` (no names) and `statsPending [{position, username}]` (the human owners still to credit; a player deleted mid-game is left out); each attempt first looks the gameId up and E11000 on the unique index means another writer won, so the stored entry (and its pending list, none once applied) is used; (2) each pending player's `$inc` is guarded in the same update: filter `statsGames: {$ne: gameId}`, `$push` of the id into `users.statsGames` (the last `STATS_GAMES_KEPT`, 50; server-only, never on the wire), so applying it twice counts once; (3) `statsPending` is `$unset` (or cut to the players whose write failed for good), so the usernames leave the record. Every step retries any failure after 1, 2, 4, 8, 16 s (every step is idempotent); a record that cannot be written at all is logged with its deltas and the stats still go in once. One chain per game per process (a second call joins it); `trackInFlight` makes a graceful shutdown wait for it. `resumePendingGameStats` (server/index.js, once after `connectDB`) finishes every record still carrying `statsPending` (a crash, an outage longer than the retries), safe while another process applies the same record. Accepted: a pending record keeps the pending usernames until it is applied or swept (seconds normally); a rename or merge of a player in that window credits nobody (the guarded update matches no account). Records from before 2026-11-15 have no `statsDeltas`. Tests: `server/socket/__tests__/gameStatsWrites.test.js` (memoryDb with failing writes and lost replies, the sweep, shutdown), realMongo (p)

## Backups and restore

Why: there are no transactions, and `users.stats` / `users.botStats` are cumulative `$inc` counters that cannot be rebuilt from `gameRecords` (records before 2026-11-15 carry scores and names, not per-player tricks, sets, faults or HSI (since then `statsDeltas` holds each seat's counters, by position, not by name), and bot games before 2026-11-13 have no records at all). A merge is partly reversible: the kept account's `mergedFrom[]` entries hold each source's `stats` and `botStats` at merge time (the tombstone has no password or sessions left, so an un-merge also needs a new password). A delete (the player's own or the admin panel's: user document gone, records anonymized to `[deleted]`), a buggy stats change, a bad manual edit or a lost volume is permanent without a backup. Two independent layers, both the owner's to run:

### Layer 1: Railway volume backups (dashboard only)

- Turn on: project canvas → MongoDB service → **Backups** tab. Schedules (pick any, several at once): daily (kept 6 days), weekly (kept 27 days), monthly (kept 89 days); **Backup now** makes a manual one, capped at 50% of the volume (5 GB volume, ~635 MB used: fine). Incremental, copy-on-write, billed like volume storage for the data unique to the backups. Railway calls the feature "still under development"; whether the Hobby plan has it is not stated in its docs (checked 2026-11-15): the tab shows it or not
- Restore: Backups tab → the dated backup → **Restore**. Railway makes a NEW volume from it, mounted at the same path; the current volume stays in the project, unmounted (so writes after that backup are still on it until you delete it). The change is staged: **Details** / **Deploy** on the canvas applies it and redeploys the MongoDB service. Downtime is that redeploy (seconds to minutes); the app keeps running meanwhile, every DB call fails after ~5 s and games go on (`dbOutage.test.js`), stats of games that end in the gap are lost, and it reconnects by itself. Everything written after the backup is lost (left on the old volume)
- Limits: "wiping a volume deletes all of its backups", restores go only into the same project and environment, and the retention is at most 89 days. Nothing here survives losing the volume, the project or the account, or a mistake found later: hence layer 2

### Layer 2: logical backup, `scripts/backup-db.js` (owner-run on your machine)

- Needs: macOS or Linux (the URI reaches the tools through `/dev/fd`), a checkout with `npm ci` (Node 24) and the MongoDB Database Tools (`brew install mongodb-database-tools`: mongodump / mongorestore / mongoexport / mongoimport 100.x; the drill used 100.16.1). mongosh is not needed
- A URI that works from your machine: the app's `MONGO_URI` is the private-network one (`MONGO_URL`, a `*.railway.internal` host), unreachable from outside. Railway databases are private by default: MongoDB service → **Settings → Networking → Public Access** adds a TCP proxy and the variable `MONGO_PUBLIC_URL`. Egress through it is billed (about one archive per backup). It exposes mongod to the internet behind the root password Railway generated: leave it on, or turn it on for a backup and off after (the proxy host/port can change; `MONGO_PUBLIC_URL` follows). Owner's call
- Run it from the linked checkout, with the URI never on screen, in a command line or in shell history (single quotes: the inner shell expands it, not yours):
  ```bash
  railway run --service MongoDB -- sh -c 'MONGO_URI="$MONGO_PUBLIC_URL" node scripts/backup-db.js --out ~/bab-backups --keep 12'
  ```
  `railway run` injects that service's variables into that one command only (use the service's name as the canvas shows it; the flags are from `railway run --help`, CLI 5.71; never tried against the project). Never `export MONGO_URI=<production>` in your shell: `merge-accounts`, `set-password`, `set-admin` and a local `npm start` all read `MONGO_URI` and would then act on production. The script reads `MONGO_URI` from the environment only (never `.env`, no default)
- What it does: refuses `--out` inside this repository or any git work tree (symlinks resolved; `.gitignore` also ignores `*.archive.gz`); hands the URI to mongodump through a pipe (`--config=/dev/fd/3`), so it is never in `ps` or in a file (a run killed or cut off by closing the terminal leaves no password behind; Ctrl-C, `kill` and SIGHUP also stop mongodump and remove the `.partial`); makes the auth database explicit (`authSource`: the URI path, else `admin`), because `mongodump --db babonline` otherwise logs in against `babonline` and Railway's root user lives in `admin` ("Authentication failed", found in the drill); writes `<dir>/babonline-<UTC>.archive.gz.partial`, refuses a dump whose `users` is missing or empty (the accounts are gone or it is the wrong database: such a dump must not pass for a backup or push good ones out with `--keep`; `--allow-no-users` overrides, never together with `--keep`), reads the whole gzip stream back, saves it under its final name without ever replacing an existing archive (names have one-second resolution: a second run in the same second is refused) and sets 0600; prints per-collection counts, size, time and SHA-256, never a document; `--keep N` then deletes all but the newest N `babonline-<UTC>.archive.gz` in that folder (nothing else). Any URI in a tool error is printed as `mongodb://***@host`. Exit 0 ok, 1 failed (nothing kept), 2 usage (nothing kept), 3 archive kept but pruning failed
- Not point in time: on a standalone mongod (no oplog) mongodump copies collections one after another while the server writes, so a game ending mid-dump can have its record without its stats or the reverse. Run it at a quiet hour
- How often: weekly, and always right before anything risky (a merge batch, deploying a stats or schema change, a hand edit in the DB, a restore). Layer 1 covers the days between
- Where to keep archives: they hold every bcrypt password hash, every session-token hash, any legacy plaintext `sessionToken` (accounts that have not signed in since per-device sessions; the server still accepts one, so an archive can hold live sign-ins in the clear), reports and the admin audit. On an encrypted disk (FileVault, an encrypted external drive) plus one copy off the machine: an attachment in your password manager, or an `age`/`gpg`-encrypted file in private cloud storage. Never the repository, never a shared or public folder, chat, issue or email. Check the SHA-256 after copying. Prune (`--keep`): deleted accounts live on in old archives until they go (see the privacy note below)

### Restoring

Always first: back up the CURRENT state, broken or not (it keeps the writes since the good archive, and undoes the restore if it was the wrong call). Then:

- **Inspect in a scratch database** (always the first step; needs a local mongod: `brew tap mongodb/brew && brew install mongodb-community`, then `mongod --port 27999 --dbpath ~/bab-restore-db` in its own terminal after `mkdir ~/bab-restore-db`):
  ```bash
  node scripts/restore-db.js ~/bab-backups/babonline-<UTC>.archive.gz --uri mongodb://127.0.0.1:27999 --into-db babonline_restore_20261115
  ```
  `--into-db` (or `--nsFrom 'babonline.*' --nsTo '<name>.*'`) restores under another name. It refuses a non-empty target unless `--drop` (drops each archived collection first), builds any missing index with `server/database.js` `ensureIndexes`, and prints counts, index names, users / merged names / saved sessions / players with stats, the newest game's time, and a sanity check (`users` is not empty, every user has a username, every account a bcrypt hash, the unique `users.username_1` could be built, i.e. no duplicate names; exit 1 otherwise). Look at documents with mongosh or Compass. The target is `--uri` (no credentials allowed there: shell history) or `RESTORE_URI`; `MONGO_URI` is never used, so a leftover export cannot aim a restore at production
- **Put back specific documents** (e.g. a wrongly deleted user), from the scratch copy, in insert mode (it never overwrites: an existing `_id` or a name taken since by a new sign-up is refused, `1 document(s) failed`):
  ```bash
  umask 077
  mongoexport --uri mongodb://127.0.0.1:27999 --db babonline_restore_20261115 --collection users --query '{"username":"Alan"}' --jsonFormat=canonical --out alan.json
  railway run --service MongoDB -- sh -c 'mongoimport --uri "$MONGO_PUBLIC_URL" --authenticationDatabase admin --db babonline --collection users --mode insert --file alan.json'
  rm alan.json
  ```
  Then **redeploy or restart the bab-online service** (canvas → bab-online → its deployment's menu → Restart or Redeploy) before telling the player: a deletion puts the name in the server's in-memory `deletedUsernames`, so until a restart every game the restored player finishes is recorded as `[deleted]` (and the leaderboard / records caches and avatar store still treat the account as gone). Games they play between the import and the restart stay `[deleted]`.
  `--authenticationDatabase admin` is required (as above), and these raw tools print the WHOLE URI, password included, on a connection error: do not paste their output anywhere. `--jsonFormat=canonical` keeps types (dates, int vs double). The restored account signs in with its old password, and its devices' saved sessions from the archive work again; its past games stay `[deleted]` and other players' block lists stay as they are now (fixing those is a one-off script: ask). For stats drift, never put an old user document back over a live one (it erases every game since): work out the per-player difference from the scratch copy and `$inc` it, with a dry run first
- **Full restore into production** (last resort: lost volume or mass damage, and no usable layer-1 backup):
  1. Back up the current state (if any) and check the archive in a scratch database (above)
  2. Stop the app's writes: bab-online service → its active deployment's menu → Remove (players see the site down; check the dashboard's wording)
  3. `railway run --service MongoDB -- sh -c 'RESTORE_URI="$MONGO_PUBLIC_URL" node scripts/restore-db.js ~/bab-backups/babonline-<UTC>.archive.gz --i-mean-production --drop'`: it shows the target host (`<-- NOT LOCAL`) and restores only after you type `babonline`. Without `--i-mean-production` any host but localhost / 127.0.0.1 / ::1 is refused (an SSH tunnel on a local port counts as local: never tunnel production to a port you restore into)
  4. Redeploy bab-online, check `/health` (`db: connected`) and sign in
  - What it loses: everything since the dump. Accounts created since (their names are free again; those players sign up again), games, stats and records, reports, admin-audit entries, reset links. Undone: password changes (an old password works again) and session revocations (redo any Sign out everywhere / reset since the dump), merges and renames. Back: accounts deleted since, including players' own deletions; delete them again (diff the usernames of the pre-restore backup against the restored database). Sessions: `users.sessionTokens` is in the dump, so every device signed in at dump time stays signed in (drilled: a pre-dump token restores after the restore); a device that signed in later signs in again
- Privacy note for the owner: `/privacy` says deletion removes data "immediately"; copies in backups remain until rotated (layer 1: up to 89 days; layer 2: your `--keep`). Adding a line such as "Copies in encrypted backups are deleted within 90 days." is the owner's decision. The App Store privacy labels describe data collected and its use, not backups, so they should not change

### Proposal: scheduled backups (not built; owner decides)

A Railway cron service in the same project (schedule `0 9 * * *`, UTC; it must exit after each run) that runs `mongodump --uri "$MONGO_URL" --authenticationDatabase admin --db babonline --gzip --archive` over the private network (no public proxy needed), pipes it through `age` with a public key only (the service can encrypt but never read; the private key stays in your password manager) and uploads the result to a Railway Bucket (S3-compatible) with a lifecycle of ~30 days. Cost at today's size: storage $0.015 per GB-month (≈ 12 GB kept ≈ $0.20/month), the upload counts as egress since buckets are not on the private network (≈ 12 GB/month), plus a few seconds of compute a day: well under $2/month. Steps: create the bucket; add a service from a small image with the Database Tools, `age` and an S3 client; set its variables by reference (`${{MongoDB.MONGO_URL}}`, the bucket's credentials, the age public key); set the cron schedule; check one run's object restores here (`age -d` then restore-db.js). Trade-off: a bucket in the same Railway account does not survive losing the account; an outside bucket (Cloudflare R2, Backblaze B2) does, at similar cost. Until then, the weekly owner-run backup above is the off-Railway copy

## CI

- CI (`.github/workflows/ci.yml`) is the only gate before Railway deploys main. ## DB reads and profile caches

- DB reads are projected (memoryDb supports projections, so tests see the real shape): signIn excludes `customProfilePic`/`stats`/`botStats`/`mergedFrom` (restoreSession also `password`); profile/leaderboard/search/records read only the fields their replies use. `handleDrawComplete` looks up the four saved pics in parallel with `getUserProfilePic(u, {randomFallback:false})` (null instead of a random pic) and the unchanged loop draws every random pic in `drawIDs` order — never let lookups draw randoms concurrently (seeded fixtures/transcripts/sim depend on the order)
- Stats scopes (owner 2026-11-13: "you can choose to see standings including human and bot games, human only, or human plus bot only ... default to human only"; `server/utils/statsScope.js`): `users.stats` stays the HUMAN-games bucket exactly as before (same fields and rules; every shipped iOS build and every existing reader sees it); a game with any `bot` or `resignBot` seat at the end (solo games, tournament tables with filler bots, a resigned seat) `$inc`s the parallel `users.botStats` (same 12 fields) for every seat with a human owner (the `getOriginalPlayer` + `ownerUsername` rule: lazy, resigned and /leave'd owners included) and inserts its `gameRecords` entry with `withBots: true`, `team1Players`/`team2Players` holding ONLY the human owners (seat order, `recordName`) and `team1Bots`/`team2Bots` the persona names of the seats without an owner ('🤖 Mary'; a team of two bots has `teamNPlayers: []`). Bots are never in `teamNPlayers`, so merge / rename / delete never touch a bot name. A lazy-only game stays human; a game with no human owner (ambient demo) records nothing and invalidates nothing. Nothing from before 2026-11-13 exists for bot games (no backfill). Readers: `getProfile` / `getLeaderboard` / `getRecords` / `getPlayerProfile` take an optional `{scope: 'human'|'bots'|'all'}` (`normalizeScope`: missing, non-object or unknown = `human`, never refused; `getPlayerProfile`'s Joi key is `Joi.any()` so `stripUnknown` keeps it and a non-string, null or long scope is normalized, not refused; `socket/index.js` forwards the payload of the three safeHandler events; their c2s contract payload stays the open property-less one, documented by examples and notes, since a payload WITH properties needs a Joi schema and their `joi: null` is frozen by the baseline). `human` = today's reply byte for byte (`profile.stats` is the RAW stored bucket, a legacy 6-key document stays 6 keys; records filter `withBots: {$ne: true}`, same projection, still three finds, the thisMonth/thisYear finds still on `completedAt_-1`); `bots` = `botStats` / `withBots: true` records; `all` = `stats + botStats` summed field by field (`sumBuckets`) / every record. The leaderboard reads every player with `gamesPlayed > 0` IN THAT SCOPE (all: either bucket) and the Population row averages all of them, but only a player with `LEADERBOARD_MIN_GAMES` (5) or more games in that scope gets a row of their own (owner 2026-11-14: hide, don't list unranked, so every shipped client is right with no app change; profiles, records and search ignore it; the web says "Players appear in the standings after 5 games." under the table; `leaderboardMinGames.test.js`, and the older leaderboard suites pin the minimum to 1 with `_setLeaderboardMinGamesForTests`). Records in bots / all: `players` = the humans then the bot personas (strings, the wire type is unchanged), and a team of two bots never holds the highest/lowest score or most/least bags (biggest win always has a human side). Echo rule: the reply carries a top-level `scope` ONLY when the request had a `scope` key (so iOS and every payload-less caller get exactly the old bytes; the web always sends one and drops a reply for another scope). leaderboardResponse / recordsResponse failures echo it too (iOS 1.2.1 build 8 files a failure under the scope that asked; the web drops a stale one); profile failures do not. `searchPlayers` rows stay human games (a lookup, not standings). Records game counts (owner 2026-11-14: "the total number of games played doesn't change when selecting this year or this month"): `totalGames` stays the scope's ALL-TIME `countDocuments` (unchanged for shipped clients) and every success reply adds `periodGames {allTime, thisYear, thisMonth}` (additive, after `totalGames`): the length of each period's find in `fillRecords`, so the same scope filter and the same server-local year / month boundaries as that period's records, no extra query, cached in the same per-scope fill (caches and invalidation unchanged); `periodGames.allTime` equals `totalGames`. Tests: `server/socket/__tests__/statsScope.test.js`, presence R20, tournamentLifecycle (filler-bot tables), realMongo (f, o), `server/admin/__tests__/botStatsMerge.test.js`
- Profile caches (`server/utils/ttlCache.js`, `profileHandlers.js`): leaderboard and records are 60 s single-flight caches, ONE PER SCOPE (`leaderboardCache[scope]`, `recordsCache[scope]`; records keyed by server-local year-month, and a month change clears every scope); a fill that overlaps an `invalidate()` is never stored; cached values are shared, never mutate them. Every `invalidateLeaderboard()` / `invalidateRecords()` clears all three scopes. Invalidated after `recordGameStats` (records after `recordGameResult`, both after the stat writes), `deleteAccount`, `updateProfilePic`/`uploadProfilePic`, an admin merge or rename. Test helpers `_peekLeaderboardCache(scope = 'human')`, `_peekRecordsCache(scope)`, `_resetCachesForTests()` (every scope). The owner CLIs (`merge-accounts`, `set-password`) run in another process: only the TTL covers them. Search stays the unanchored case-insensitive regex (it walks the `username_1` index keys; no `usernameLower` field by choice — no backfill, no Alan/alan collisions); a trimmed query longer than 50 answers `[]` without a read

## Soft limits

- Soft limits (`rateLimiter.limits`, per socket): `getLeaderboard`/`getRecords` 10/10 s are checked inside their handlers and over the limit reply with the cached (even stale) page OF THE REQUESTED SCOPE, its fill in flight, else the ordinary `{success:false, message}` — never `serverError` (one budget for every scope: fast switching counts against it; the web control coalesces quick switches, 200 ms); `searchPlayers`/`getPlayerProfile` 30/10 s through `asyncHandler` (`serverError {code:'rateLimit'}`, a web toast; Joi since V1_REMOVALS #18, as for `joinLobby` (a uuid) and `removeBot` (a `bot:` id; `removeBotFromLobby` also refuses a human member); both web-only). Session and table entry (2026-11-15, generous: every reconnect is a new socket): `restoreSession`/`rejoinGame` 10/min, `joinLobby`/`joinAsSpectator` 20/30 s, `updateProfilePic` 30/min through the wrappers, `getProfile` 20/10 s checked in `profileHandlers.getProfile` (no schema); the no-payload `joinMainRoom` 30/min, `playerReady`/`playerUnready` 20/10 s, `leaveLobby`/`addBot` 20/30 s through `safeHandler(fn, { limit })` (checked at the socket event only, never on internal calls such as joinMainRoom leaving a lobby); all answer `serverError {code:'rateLimit'}` over the limit (a refused restoreSession never gets a `restoreSessionResponse` failure, which makes iOS forget its token). `rateLimiter.unlimited` lists the wrapped keys left unlimited on purpose (`forceResign`, `removeBot`); any other key with no limit warns once per key outside production (`eventLimits.test.js` checks every `socket.on` in index.js: a wrapper key with a limit, a `safeHandler` limit, one of the events checked inside their handlers (clientHello, getProfile, getLeaderboard, getRecords, the voice signals), or `unlimited`). Per-IP and server-wide sign-up buckets: `docs/claude/server-accounts.md`. `contract/src/c2s.js` mirrors the wrapper metadata (contract.test checks it)

## Avatars

- Avatars (docs/avatars.md, invariants I1-I6): clients that send `clientHello {caps:['avatarUrl']}` (`server/socket/clientInfo.js`, `socket.data.client`; web sends it from `client/src/utils/avatar.js`) get null custom-picture slots plus additive `avatarUrls`/`avatarUrl` (`GET /avatar/:username?v=`, `server/routes/avatar.js`: immutable only on the current version, uniform 404, per-IP bucket via clientIp); every other socket (the App Store build, old web bundles) gets the small derived inline WebP in the same slot. Renditions are derived lazily in memory (`server/avatar/avatarStore.js`, sharp pinned exactly at 0.34.5 so the lockfile's `@img/sharp-*` platform packages match; `warm` from getUserProfilePic, never blocking, no RNG) and mapped at emit time (`server/avatar/avatarWire.js`); room broadcasts (positionUpdate, playerActiveMode) stay ONE emit with inline + URL. Stored `customProfilePic` values are never rewritten; new uploads are stored as the canonical WebP. Kill switches: `AVATAR_LEGACY_INLINE=raw`, `AVATAR_PIPELINE=off` (default off under Jest: tests opt in with `avatarStore.configure({enabled:true})` + `_reset()`). Stock art: `client/assets/profileN.png` 192 px (same paths: iOS 1.2.0 loads them, so V1_REMOVALS #19 E keeps them) and `client/assets/avatars/v1/*.webp` (immutable; new art goes to v2); web renders every picture through `avatarSrc`/`applyAvatarImg` only. Since V1_REMOVALS #19 A-D, F (2026-11-12) no payload carries a picture inline for anyone: slots are stock numbers or null, custom pictures only `avatarUrls`/`avatarUrl` (the cap no longer picks a shape; `AVATAR_LEGACY_INLINE` and the placeholder are gone; `AVATAR_PIPELINE=off` now hides custom pictures)
