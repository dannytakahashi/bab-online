## Key Architecture Patterns

**Server:**
- `GameManager` singleton manages the main room, lobbies, all active games and tournaments (the matchmaking queue is gone: V1_REMOVALS #2)
- `GameState` encapsulates all state for a single game
- `rules.js` contains pure, stateless game logic functions (highly testable)
- Socket handlers wrapped with validation, rate limiting, error handling
- Timers never call into server code bare: an uncaughtException exits the process (exit 1, Railway restarts it, every game is dropped), so use `utils/safeTimer.js` `safeTimeout(fn, ms, label)` / `safeInterval` (logs and carries on) or a game's `game.setTimer`; `safeTimer.test.js` fails on a new bare timer (`docs/claude/server-infra.md`, Deploys)
- Socket.IO server options live in `server/socket/serverOptions.js` (cors + `connectTimeout` 10 s instead of the 45 s default: an engine that never joins the namespace is dropped, which bounds the iOS 1.1.0/1.2.0 stall after a long background below; `connectTimeout.test.js`)
- (The iOS stall after a long background: `iOSClient/CLAUDE.md`, iOS reconnect after a background.)

## Key Data Structures

**Card:**
```javascript
{ suit: 'spades'|'hearts'|'diamonds'|'clubs'|'joker', rank: '2'-'A'|'HI'|'LO' }
```

**Server GameState:**
- `seats`: {1..4 → seat record} (`server/game/SeatState.js`): who controls the seat and whether its owner is present (see Important Implementation Details)
- `players`: Map<seat socketId → {username, position, pic}> and `positions`: {pos → seat socketId} — a derived index of `seats` (display identity: the owner for a human seat, else the bot), written only by the seat transitions
- `entrants`: Map<socketId → {username, isBot, presence connected|disconnected|left}> before seating (set by `createGame`, null once 4 seats exist)
- `hands`: {socketId → card[]}, `bids`: {position → bid_value} during bidding, then {team1, team2}
- `stage` (internal, authoritative): `CREATED → DRAWING → DRAW_RESOLVING → TEAMS_ANNOUNCED → (DEALING → BIDDING [→ REDEAL → DEALING → BIDDING] → PLAYING ⇄ TRICK_RESOLVING → HAND_RESOLVING) ×13 → ENDED`, any live stage `→ ABORTED` (`server/game/GamePhase.js`). `epoch` bumps once on ENDED/ABORTED
- `phase` / `bidding`: read-only wire projections of `stage` — `phase` is 'waiting'|'drawing'|'bidding' (never 'playing'; it stays 'bidding' through play), `bidding` is false only from the end of bidding to the next deal
- `trump`: card, `isTrumpBroken`: boolean
- `playedCards`: [pos1Card, pos2Card, pos3Card, pos4Card]
- `tricks`: {team1: count, team2: count}

**Bid Values:** '0'-'13' for numbers (a number may not exceed the hand size, so '13' only on the 13-card hand: owner 2026-11-11, "technically legal, just very unlikely"; a plain 1x bid of 13 tricks), 'B'/'2B'/'3B'/'4B' for bores (2x/4x/8x/16x multipliers; each level needs the one below on the table and may be bid once per deal: `isValidBid` refuses a skipped or repeated level, owner 2026-11-11). `rules.BID_VALUES` is the one list (the Joi `playerBid` schema and `GameState.validateBid` use it / `isValidBid`); Joi takes '13'/13 on any hand and `isValidBid` refuses it below 13 cards (`actionRejected invalid_bid`). For the lead every bore outranks a numeric 13 (`findHighestBidder`); bots never bid 13 (`server/socket/__tests__/bid13.test.js`)

## Game phase FSM

- Game phase FSM (`server/game/GamePhase.js`, `GameState`): the stage changes only through `game.transition(from, to)` (every call site reads `if (!game.transition(F, T)) return;` — an illegal call throws under Jest / `BAB_FSM_STRICT=1`, logs and fails closed in production), `tryTransition` (the DRAWING → DRAW_RESOLVING latch, so the draw resolves exactly once) and `terminate(io, ENDED|ABORTED, event, payload)` (final event out first, then epoch bump + cancel all game timers). Never write `game.phase`/`game.bidding` (getters; a write is a reported violation) and never gate on flags — gate on `game.stage` (`acceptsTurnInput()`, `actionTypeForTurn()`, `isPreSeating()`). Lifecycle waits use `if (!(await game.pause(ms))) return;` (presentation holds: `game.hold(kind, ms)`, see Pacing) and timers use `game.setTimer(key, ms, fn)` (`grace:<pos>` per-seat reconnect grace, `abandon`, `draw:watchdog`, `resume` (trick/hand hold); `afk:<pos>` the turn watchdog, see AFK below; `stall` the progress watchdog, see Bots; bot bid/play/draw/chat stay in `BotController.pendingActions`), so nothing runs or emits after end/abort; BotController timers check `game.epoch`, and `broadcast`/`sendToPlayer` drop everything from a terminal game. `recordDraw` is the only writer of draw state. Abort only through `socket/gameLifecycle.abortGame(io, game, reason)` (abortGame to the room incl. spectators → ABORTED → `GameManager._retire`: bots, room, every `playerGames` entry for the game → lobbiesUpdated → DB/tournament follow-up); the draw starts only through `gameLifecycle.beginDraw` (also auto-draws for sockets that left/disconnected during the pre-draw countdown). The end path sends `gameEnd` before persisting stats. Jest's `server/testUtils/fsmGuard.js` fails any test that records a violation; `BAB_FSM_CHECK=1` runs `validateGameState()` (per-stage + seat invariants) on every stage and seat transition and records `_history` (`server/socket/__tests__/chaos.test.js`, `lifecycle.test.js`, `wireProjection.test.js`)

## Bots

- Bots have socketIds like `bot:{username}:{uuid}`, use `BotStrategy.js` for AI. Card play is contract-aware: `processBotPlay` passes a play context (team bids/tricks/bores) into `decideCard`. Personalities (`personalities.js`) define `bidStyle` + `playStyle` consumed by the strategy; Mary is the sim-tuned optimal baseline, the others are slight measured variations. Play reads the unseen hands through `BotStrategy.buildCardView` (voids, who is out of trump, caps on each player's best trump, all from the bot's own card memory) and `PLAY_TUNING` holds the switch for each play rule that uses it (low ruffs, boss / low trump leads, void rules; `sim/README.md` "Play inference" and "Combined play"). Strategy changes must be benchmarked with `npm run sim` against the frozen legacy snapshot (`sim/legacyStrategy.js`)
- Bidding on 2+ card hands (no bore on the table) is expected-value bidding over fitted tables in `bot/bidModel.js` (GENERATED: `simulate.js --records` then `sim/fitBidModel.js`; refit after any bidding or card-play change, recipe in `sim/README.md`). Any bot-decision change also changes the wire golden (`UPDATE_WIRE_GOLDEN=1`) and the iOS event-log fixtures (`npm run ios:fixtures`, then the iOS replay XCTests; `Fixtures/kept/kept-bots-s12.json` is kept by hand for the tests that need a B + 2B hand or an over-trump, `iOSClient/CLAUDE.md` iOS table)
- Card play with 7 cards or fewer in hand is searched (`bot/playSearch.js`, called from `BotStrategy.selectOptimalCard`): the bot samples deals of the unseen cards (consistent with shown voids, forced plays under a HI-joker lead, a last seat that lost a trick (only a read, since nothing forces a void last seat to ruff: lifted for good once that player shows a card above it, and dropped when it leaves too few deals), and, by weighting, the bids), solves each one exactly (all hands open) and plays the card with the best average hand score (own points minus the opponents' under the real contract); the rule-based card stands on an exact tie, above 7 cards, and when the bot's memory does not cover the whole hand (a lazy/resign bot seated mid-hand). An exception inside the search also plays the rule card: it counts in `SEARCH.errors` (`simulate.js` prints `searchErrorCount`) and `BotStrategy.noteSearchError` logs a `gameLogger.warn` for the first one and then at most one per 5 minutes (`SEARCH_ERROR_LOG`; error message, hand size and the count held back, never a card). Last to play it only considers winners when the trick can be won. A decision is a pure function of what the bot has seen: the sampler is seeded from the position and the effort limit is a node count (`SEARCH.nodeBudget` 200,000, hard stop 300,000: about 10 ms worst case on a laptop core), never a clock or `Math.random`, so sims, goldens and fixtures stay reproducible. Any change to it is a bot-decision change (re-record as above). `Math.*` is bound to locals there on purpose: lookups through Jest's sandboxed global made the solver 10x slower in tests. `ambientGameVisibility.test.js` turns the search off for its full-cycle test (about 20,000 bot plays on fake timers)
- One path for bids and plays (humans and bots): `GameState.applyBid(position, bid)` (stage/turn → `not_your_turn`, a repeat → `already_bid`, `isValidBid` on the upper-cased bid → `invalid_bid`, then `recordBid`) and `GameState.applyPlay(position, card, socketId)` (= `checkPlay`: stage/turn, `validateCardPlay` → `invalid_play` with its error, an occupied slot → `already_played`, `rules.isLegalPlay` → `illegal_card`; then the card leaves the hand (its `removeCardFromHand` result is checked) and goes on the table, lead and trump-broken updated). The reasons are the `actionRejected` reasons the human handlers send; a refused `illegal_card` still moves the card to the end of the hand, as before the refactor (the iOS fixtures' snapshots pin that order). `playerBid`/`playCard` keep their own rejections, logs and the `restorePlayerState` resend; `processBotBid`/`processBotPlay` keep their stale-state skips. Bot failures (no longer logged and dropped): a strategy that throws, or a bid/card the same checks refuse (a card checked with `checkPlay` first, so a bot's hand never reorders), logs `gameLogger.error` 'Bot bid refused, bidding the safe bid' / 'Bot play refused, playing the first legal card' (game id, position, bot, stage, hand size, the choice, reason / error, running count) and plays `rules.safeBid(playerBids)` ('0', or '1' for the last bidder over three zeros so failing bots cannot redeal forever) / `rules.firstLegalCard` (hand order); `botController.fallbacks {bid, play}` counts them since startup. `simulate.js` applies the same checks and fallbacks (`incidentCount`, `bidIncidentCount`, `exceptionCount`, `searchErrorCount`: all 0 when healthy). Tests: `server/socket/__tests__/botFaults.test.js`
- Progress watchdog (`server/socket/progressWatchdog.js`, game timer `stall`): a bot's turn or a server-only stage (DRAW_RESOLVING, TEAMS_ANNOUNCED, DEALING, REDEAL, TRICK_RESOLVING, HAND_RESOLVING) must move on by itself. Armed in `triggerBotIfNeeded`'s bot branch and when DRAW_RESOLVING / TRICK_RESOLVING / HAND_RESOLVING open, cleared by its human branch (a slow human is the AFK watchdog's, never this one's: a solo game's human may sit forever); it compares `game.turnKey()`. No progress for `STALL_MS` (90 s): logs `gameLogger.error` 'Game stalled' {kind bot|resolving, stage, position, controller, turnKey, retry} and retries a bot turn once (`triggerBotIfNeeded` again; a resolving stage is not retried, its continuation may have half-run); still the same `STALL_RETRY_MS` (30 s) later: 'Game stalled, aborting' and `abortGame(io, game, 'Game stalled')` (`abortGame {reason}` is a free string on the wire, both clients just show/leave), which a tournament table reports like any aborted table (`tournamentGameComplete {aborted: true}`, the running scores recorded (Tournament scoring below), the round can finish). A watched state that moved on without an arm point (e.g. stuck in DEALING, or a bot's play landed and its continuation failed before triggering the next seat) is found at the next firing and watched for only `STALL_RETRY_MS` from there (it may already be up to 90 s old), so its retry comes by 90 + 30 s and its abort by 90 + 60 s. `processBotBid` skips a seat whose bid is already recorded (a retry after the post-bid step failed) as stale state, like `processBotPlay`'s occupied slot, not as a strategy fallback. Not a presentation delay, so not in `pacing.js`: every profile's legitimate waits are a few seconds; env `GAME_STALL_MS` / `GAME_STALL_RETRY_MS` override at every arm (0 disables), which the tests use. Terminate cancels it with every game timer. The ambient game's 90-minute recycle (`server/demo/ambientBots.js`) stays as the last resort
- Lazy-bot timers: lazy, resign and draw-leaver bots are seat bots and schedule through `BotController.scheduleBotAction` (keys `${gameId}:${botSocketId}:bid|play|draw|chat:<n>`); `/active` → `unregisterBot` → `cancelBotActions` clears every key of that bot (chat included) and `cleanupGame` clears by game prefix (srv-15; `botTiming.test.js`)

## Socket rooms and draw watchdog

- Socket rooms: players join `game:{gameId}` for broadcasts; tournaments use `tournament:{tournamentId}`
- Draw watchdog: 30s after DRAWING opens (`draw:watchdog`, armed by `beginDraw`, cleared by `handleDrawComplete`) every entrant that still has not drawn is auto-drawn (`youDrew` to a connected one); disconnected/left entrants are auto-drawn immediately and bots draw within ~4s, so the draw always ends within ~30s

## Seats and presence

- Seats (`server/game/SeatState.js`, `GameState.seats`, orchestration in `server/socket/seatLifecycle.js`): one record per position — `controller` human | lazyBot | resignBot | bot (native lobby/tournament/ambient bot, no owner) and `presence` connected | grace | resignable (human seat) / connected | away | gone (lazy/resigned seat) / none (native bot), plus `ownerUsername`/`ownerPic`, `ownerSocketId` (the owner's ONE live socket, set exactly when connected), `ownerView` ('seat' after /lazy at the seat, 'watch' after a rejoin/spectate), `seatSocketId`, `bot`, `lastPersonality` and timestamps. A bot-controlled seat's seat socket (positions/players/hands key) is the bot's `bot:` socket; the owner socket is separate, so lazy play goes through `BotController.scheduleBotAction` like any bot and the owner's socket can't bid/play over it. Seats change only through the GameState transitions (`createSeat`, `seatDisconnect` — a no-op unless the socket is the current owner socket — `seatGraceExpired`, `seatReconnect`, `seatWatch`, `seatGoLazy`, `seatGoActive`, `seatResign`, `seatLeave`; `forceSeat` is test-only), each checked against the SeatState edge table (illegal → 'seat-illegal' violation); `gone` is absorbing. `seatLifecycle` functions do transition → playerGames/room → emits → `maybeAbort`; handlers only dispatch. `pickBotPersonality` never reuses a name/personality already at the table (lazy, resign and draw-leaver bots)
- `playerGames` maps exactly: connected entrants (before seating), every seat's `ownerSocketId`, and every bot-controlled seat's bot socket — never a dead or stale socket. Pure spectators live only in `gameManager.spectatorGames` (one game per socket; `addSpectator` / `leaveSpectating`, also on `joinMainRoom` and `returnToTournament`) and `game.spectators`; a socket mapped to a game is never a pure spectator. `chatMessage` resolves the sender's role (owner / entrant / spectator) first, so a spectator or stale socket can never /active, /lazy or /leave a seat — with one exception: a pure spectator recorded under the owner's name may `/active` a bot-controlled seat whose presence is `away` (no owner socket attached; `seatLifecycle.reclaimSeat`, e.g. the phone after the laptop that took the seat closed). The newest socket owns a seat: a rejoin while an older socket is attached moves the seat and unmaps the old one (a watched seat demotes it to a pure spectator). `rejoinGame` refuses a socket that dropped during its session lookup or is mapped to another game. A socket leaves spectating before it becomes a seat owner (the seat transition's invariants hold throughout). `game.offerPos` is the offer present clients hold, including one `replayPresenceTo` handed a returner, so `reofferAfter` moves it when that seat comes back
- In-game leave is a chat command (`/leave`, `/lazy`, `/active`) routed through `chatMessage` — both clients' Leave buttons send `/leave`. At a human seat `/leave` = `/lazy` + leave: the bot keeps the seat (lazyBot/gone) and rejoining a gone seat gives `rejoinFailed` (its room log line is "<name> left the game. <bot> is playing for them.", not the /lazy line); from a lazy/resigned owner's socket (either view) it is the same permanent leave. What Leave says (owner, 2026-11-12): when no other owner is connected or returnable, `maybeAbort` ends the game at once, so iOS `State/Table/LeaveOutcome.swift` words the Leave alert and the /leave help from the seats (a bot finishes / "leaving ends the game" / at a tournament table, its game ends and you stay in the tournament; the alert's "no score for this round" predates the 2026-11-15 scoring, under which the leaver scores min(running, 0): Tournament scoring below) and the web's /leave help names both outcomes (`GameLog.js`; the web keeps no seat presence). A lazy/resigned owner's seat can go `gone` with no event (a human seat's /leave broadcasts only `playerLazyMode`, an already-lazy owner's nothing; `gone` shows only in snapshots), so when such seats are the only other owners iOS hedges (`.unsure`: a bot finishes unless everyone else left too) and the alert asks for a snapshot (`LocalAction.leaveAsked`, request id `leave-N`; another seat's `playerLazyMode` or `playerResigned` while it is up asks again, also when it opened definite: `PlayersSlice.leaveCheck` is `.settled`, not `.idle`, while the alert is up) that settles it (`leaveCheck` verified); an open alert keeps its first message, so `LeaveAlertFlow` holds the alert until that reply (at most 1.5 s, then hedged), and an open alert whose check goes pending holds its words until the reply (at most 1.5 s) and closes/reopens once only if the settled words differ. The alert is a UIKit `UIAlertController` (`Views/Game/LeaveAlertPresenter.swift`), not SwiftUI's `.alert`: closed and presented again, SwiftUI finished the first dismissal after the second presentation and set `isPresented` false under the new alert, whose Leave Game (now "Exit Game", title "Exit game?", #235) then sent no /leave (verifier 2026-11-13); the reopen runs from UIKit's dismissal completion and each controller's buttons act only for it. `LeaveAlertUITests` drive both reopens in fixture mode (`-uiLeaveDrive settle|hold`; sent chat in the `fixture.sent` probe). README's `/leave` row says the same. Before seats exist (countdown, draw) it marks the entrant left: `handleDrawComplete` seats a bot for it (resignBot/gone) and a draw-phase disconnect is seated in its 60s reconnect grace (announced with `playerDisconnected` after `positionUpdate`)
- Disconnect / grace / abort: a human seat's owner dropping starts its own `grace:<pos>` (60s); on expiry the seat is resignable and, if any owner is connected, the room gets `resignationAvailable` (`offerPos`). `forceResign` needs a resignable seat (refused during grace with 'Player is not disconnected') and a connected owner (a lazy owner may ask); after a resign, or when the offered seat comes back, the oldest other resignable seat is offered again. Rejoiners and `/active` watchers get the other seats' `playerDisconnected` and the current offer replayed privately (iOS shows its banner only from `playerDisconnected`). A lazy/resigned owner dropping makes the seat 'away' (no `playerDisconnected`). `seatLifecycle.maybeAbort` is the only presence-driven abort: a seated table with owners aborts at once ('All players left') when no owner can ever return, and after 60s (`abandon`, 'All players disconnected') while no owner is connected; native-bot/ambient tables are never presence-aborted
- Turn timeout / AFK (owner, 2026-11-11; `seatLifecycle.armAfk`): a connected human who neither bids nor plays within `AFK_TIMEOUT_MS` (`SeatState.afkTimeoutMs()`: 90 s for every game with another human, tournaments included; never a solo casual game, owner 2026-11-13 "in a solo game (player plus 3 bots) the player shouldn't get booted to spectating after 90s": `seatLifecycle.afkExempt` = `pacing.humanOwnerCount(game) <= 1` and not a tournament table (the round waits for every table), checked at every arm and at firing; env `AFK_TIMEOUT_MS` overrides at every arm, 0 disables) goes lazy exactly as with /lazy (`goLazy(..., {reason:'afk'})`: playerLazyMode + the log line "<name> was idle and <bot> is playing for them. Type /active to return."; web hides the bid sheet and shows its lazy pill, iOS 1.1.0 shows "Spectating — type /active to take back control" with no button, both return with /active). Armed in `triggerBotIfNeeded`'s human branch (every human turn: bid, play, first turn after the hold), on `/active` and on a reconnect from grace at the seat's own turn (a newer socket taking a connected seat keeps the running clock); the timer re-checks seat human/connected, turn open and the same `game.turnKey()` before firing. Cleared by the seat's accepted bid/play (a refused action does not reset it), any other seat's turn, /lazy and /active (controller change), the owner dropping (presence leaves connected: grace timers own that), and end/abort (terminate cancels game timers). Crediting is the /lazy crediting (same `seatGoLazy`): stats, the gameRecords entry (leaderboard, records) and tournament round scores go to the owner (`getOriginalPlayer`), while the `gameEnd` score screen lists the bot persona at a seat a bot holds at the end, as after /lazy. Stats bucket (owner 2026-11-13, `docs/claude/server-infra.md` Stats scopes): a game with any `bot` or `resignBot` seat at the end (solo, tournament tables with filler bots, a resigned seat) goes to every owner's `users.botStats` and a `withBots` gameRecords entry (bot personas in `teamNBots`, never in `teamNPlayers`); a lazy-only game (AFK, /lazy, /leave) stays a human game (`users.stats`); a game with no human owner (ambient) records nothing. A resigned owner, or a draw-phase leaver seated as a resignBot, is credited a bot-bucket game they did not finish, by the same ownerUsername rule. Tournament round scoring is unchanged. Tests: `server/socket/__tests__/afkWatchdog.test.js` (incl. a 13-card last hand ended under AFK vs /lazy); the race/chaos runs keep the 90 s default (longer than any zero-pacing wait)
- A lazy or resigned player who rejoins (`rejoinGame` or `joinAsSpectator`) watches their seat (`rejoinSuccess` with `isLazy`, seat `gameStart` with the hand each deal); `/active` from that owner socket makes the seat fully human again (the bot is released with all its timers). `/active` re-sends `updateTurn` at the seat while a turn is open (BIDDING/PLAYING, not during trick/hand resolution); from the watch view it sends `restorePlayerState` instead. A repeated rejoin from the watching socket is idempotent

## Lobby seats

- Lobby seats are one per username (`GameManager.findStaleLobbySeat` / `takeOverLobbySeat` / `evictStaleLobbySeat`): a half-open reconnect leaves the old socket alive on the server for up to ~45 s (pingInterval + pingTimeout) and a same-device restoreSession never kicks it, so when the new socket sends `joinLobby` (web ClientSession re-sends it after every restore), the seat moves to it in place (same position, a full lobby still lets its own player in; only that player's ready flag resets, since both clients open a re-entered lobby as not ready). Joining or creating another lobby gives the old seat up as a leave. The old socket loses its `playerLobbies` entry, gets `leftLobby`, and the others get `voicePeerLeft` for it (`lobbyHandlers.releaseStaleLobbySeat`); its later disconnect finds no lobby. Tournaments already reattach by username (`TournamentState.reattachPlayerByUsername`); creating or joining ANOTHER tournament gives up a lobby-phase membership an older socket holds as a leave and is refused while that one has begun (`GameManager.giveUpStaleTournament`). Reload grace (owner live check 2026-11-11): a transport disconnect holds a human lobby seat for `GameManager.LOBBY_SEAT_GRACE_MS` (30 s; `suspendLobbySeat`: its ready flag resets, the socket loses its mapping, the timer lives in `gameManager.lobbyGrace`, never on the wire objects); the player's next socket re-entering takes it back through the same takeover, otherwise `expireLobbySeat` removes it as a leave (an empty or bots-only lobby is deleted). A sign-out / account switch leaves at once (`handleDisconnect(..., {lobbyGrace: false})`). While a seat is held every playerReadyUpdate and joinLobby's lobbyCreated carry an additive top-level `reconnecting: [usernames]` (lobbyMember is a frozen baseline $def); web shows "Reconnecting…". The web tab keeps the lobby id in sessionStorage `lobbyId` (ClientSession `noteLobby`), so a reload re-sends joinLobby after the restore. iOS (the next build after 1.2.1 build 9) re-sends it after a restore that finds no game while its lobby screen is up (in memory only: a relaunch goes to the main room), and never sends joinMainRoom then; 1.2.0 and 1.2.1 up to build 9 go to the main room and the seat expires (`iOSClient/CLAUDE.md`, Lobby re-entry after a reconnect). Tests: `server/socket/__tests__/lobbyReentry.test.js`, `lobbyGrace.test.js`, `duplicateEntrant.test.js` (every join path, old socket alive and dropped), `client/src/reload/lobbyReload.test.js`
- Lobby start (owner report 2026-11-13, "ready before adding all bots"): a lobby starts when all 4 seats are ready, from either of two paths that share ONE tail, `lobbyHandlers.startLobbyIfAllReady` (LOBBY_START_MS, `startGameFromLobby` re-validates, bots registered, room joins, `allPlayersReady`, countdown, `beginDraw`). `playerReady` readies the bots whenever the lobby has 4 players (unchanged); `addBot` calls `GameManager.readyBotsIfHumansReady` and readies them only when the bot fills the lobby and every human is ready with no seat held for its grace, so Ready first, then Add Bot until full, starts the game. Event order on that path: `playerReadyUpdate` (the plain variant, all 4 ready) → `lobbiesUpdated` → `allPlayersReady` → `startDraw`, what both clients already handle. A held (reconnecting) seat is never ready, so it keeps the lobby waiting as on the ready path. `removeBot` unreadies only the remaining bots; the humans keep their ready flags (iOS 1.1.0/1.2.0 keeps a local `isReady` it never reads back, so a reset there left it showing "Unready" over a server-side unready seat), while a human leaving still resets every flag. Tests: `server/socket/__tests__/lobbyReadyThenBots.test.js`

## Tournament lifecycle

- Tournament lifecycle (`server/socket/tournamentHandlers.js`, `TournamentState`): `tournament.epoch` is the start generation, like `game.epoch` — `beginStart()` (phase 'starting', epoch++) on Begin/Next round, `retire()` (epoch++) inside `GameManager.deleteTournament`, which also drops every `tournamentGames`/`playerTournaments` entry and returns the tables still live. `startTournamentRound(io, t, round, epoch)` re-checks `t.isLive(epoch)` (and that the id still resolves to `t`) after EVERY await and stops — aborting any table still alive, creating and sending nothing more. Shape: announce (`tournamentRoundStart`, 1.5s) → create every table synchronously (game, mapping, bots, round entry, game-room joins) → one `Promise.all` of `setActiveGame` → `tournamentGameAssignment` + `allPlayersReady` → one shared 2s countdown (`game.pause` per table) → `beginDraw` for all, so every table starts its draw at the same instant and the round's game set is final before any table can finish. `cancelTournament` works in any phase and does the whole in-memory teardown synchronously, before its first await: `deleteTournament` → `abortGame(io, table, 'Tournament cancelled')` for every live table → `tournamentCancelled` to the tournament room → room leave → lobbiesUpdated, then the scoped DB clears (`clearActiveTournament(username, tournamentId)`). Clients rely on that order: abortGame then tournamentCancelled lands web and iOS in the main room (iOS answers abortGame with `returnToTournament`, which finds no tournament → `tournamentLeft` + `mainRoomJoined`). A tournament game resolves exactly once (`handleTournamentGameEnd` deletes the mapping first); the gameEnd path and the abort path (`handleAbortedTournamentGame`) record scores only while the game is still mapped (into `roundOfGame`'s round; a cancel unmapped it, so a cancelled tournament records nothing), both through `game/tournamentScoring.recordTableScores`, before `handleTournamentGameEnd` can complete the round. Leaving the tournament before your table is seated leaves the table too; the last member leaving aborts orphaned tables; `clearActiveGameForAll` also clears pre-seating entrants (`server/socket/__tests__/tournamentLifecycle.test.js`)
- Tournament scoring (owner 2026-11-15; `game/tournamentScoring.js`, `TournamentState.scoreMissedRound`): a finished table scores each current member at it their team's final score (unchanged). An aborted table scores the team's running score (`game.score` at the abort) for everyone at it, except a member who LEFT (seat `gone`: /leave, a draw-phase leaver's resignBot; or no longer a tournament member: left the tournament while seated), who scores `min(running, 0)`; so a stall abort ('Game stalled') or 'All players disconnected' with no leaver scores everyone's running score, and two losing partners who both /leave score their negative. A former member's row is scored too (shown, never a winner: `getWinners` takes members only). Before seating an aborted table scores its entrants 0. Details are additive on `roundDetails` (`aborted: true`, `left: true`; open rows). At round completion (`completeRound`) every member without a score that round (sat out, disconnected at the start, at no table) scores the round's lowest recorded score (0 if none; detail `missed: true`), so a leader who closes the tab before the last round no longer sits it out on a 0. Accepted residue of the owner's rule: leaving at 0-0 (the first hand) scores 0, which beats a round's negative lowest. Tests: `server/socket/__tests__/tournamentScoringLiveness.test.js`
- Tournament liveness (owner 2026-11-15; `socket/tournamentLiveness.js`, timers on the tournament: `t.setTimer('readyDeadline' | 'hostIdle')`, `safeTimeout` with unref, all cleared by every `beginStart` and by `retire`, each re-checking its condition when it fires; env `TOURNAMENT_READY_DEADLINE_MS` (default 120000) / `TOURNAMENT_HOST_IDLE_MS` (180000) read at every arm, 0 disables). Ready deadline: `broadcastRoundOutcome` arms it when a round completes (only `completeRound` sets a new one: `startRound` keeps it, so a rolled-back start re-arms what is left, and `rollbackRound` sends `tournamentRoundComplete` again (ready cleared) plus `tournamentReadyUpdate` so the members who sat out leave the round screen); past it `TournamentState.canBegin()` lets the host's `beginNextRound` start the round (`startNextRound`) with the host, who need not have readied (pressing Begin puts the host in), and the ready members (before it, and in the lobby phase, every connected member must be ready, as before); the members not ready at Begin are left out (`startTournamentRound` `sitOut`) and score the round's lowest. At the deadline the room gets `tournamentReadyUpdate {readyDeadlinePassed: true}` and the notice "Players who are not ready will sit out the next round." (only while someone is not ready); every between-rounds `tournamentReadyUpdate` and `getClientState` carry `readyDeadlinePassed` (additive). Host hand-off: in the lobby or between rounds, a connected host idle for 3 minutes while every other connected member is ready (at least one), or, past the ready deadline, while any other member is ready (Begin would start without the host; an extension of the owner's "every other member ready", so one AFK member cannot hold the role on an idle host), loses the role through `transferCreator({preferReady: true})` (a ready member first, else the disconnect rule). Announced as a host leaving: `tournamentPlayerLeft {username: old host, players, newCreator, reason: 'hostIdle'}` (reason additive) + the notice "<old> was idle, so <new> is now the host." + lobbiesUpdated. Server start: an iOS 1.2.0 host's Begin still needs everyone ready, so past the deadline the hand-off alone cannot start the round. At most one hand-off per between-rounds wait (`handedOffThisWait`); past the deadline, a host idle 3 minutes after that hand-off, or with no other member ready to hand to (and at least one connected member ready, the host included), gets the round started by the server (`startForIdleHost` → `startNextRound` with the ready members; a host who is not ready sits out) with the notice "<host> was idle, so the next round starts with the players who are ready." Worst case: round end + 2 + 3 + 3 minutes. The host's ready / unready / chat restarts the clock; every readiness, membership, host and phase change re-evaluates it (`refreshHostIdle`: join, leave, disconnect, ready, return, round outcome, deadline, rollback). Never during a round. Web: Begin enabled past the deadline as "Start with ready players", members not ready (the host aside) listed "Sitting out", a host who loses the role loses Begin / Cancel in place (`TournamentLobby.js`). iOS 1.2.0: no Swift change (`iOSClient/CLAUDE.md`). Tests: `tournamentScoringLiveness.test.js`, `client/src/ui/screens/TournamentLobby.test.js`, `client/src/reload/tournamentHostHandoff.test.js`
- Tournament server notices (spectateTournament's "X is now spectating", rollbackRound's "Round could not start", the ready deadline's and the hand-off's) go out as `tournamentMessage` built by `systemLine` (`tournamentLiveness.js`): username 'System' plus `system: true` and `type: 'system'` (additive 2026-11-15; `tournamentChatLine` $def, held additively by `additiveOnly.test.js`). A player's line never carries either, so a legacy account named "System" cannot pass for the server (the name is reserved for new sign-ups: `docs/claude/server-accounts.md`). Web styles by `system` alone (`TournamentLobby.js` `.chat-line.is-system`: the message without a name, and a blocked "System" player never hides a notice); iOS 1.2.0 reads `type` (ChatMessage.from) and already shows `.system` lines dim, without the name and without the report/block menu, so no Swift change; but it drops a line from a blocked username before reading `type`, so an iOS player who blocked a legacy "System" account loses the notices too (accepted). Tests: `tournamentNotices.test.js`, `TournamentLobby.test.js`
